# React: структурированный конспект

> Во всех примерах подразумевается современный React с функциональными компонентами и Hooks. Для JSX в новых проектах отдельный `import React from 'react'` обычно не нужен.

## Что такое React

React это JavaScript-библиотека для создания пользовательских интерфейсов.

Если совсем просто, React отвечает в первую очередь за вопрос:

"Как удобно описывать интерфейс как набор компонентов и обновлять его, когда данные меняются?"

React не пытается быть всем сразу. Это не готовый фреймворк "на всё". Из коробки он в основном решает задачу рендеринга UI. Всё остальное обычно добирается отдельно:

- маршрутизация
- работа с сервером
- управление серверным состоянием
- анимации
- формы
- сборка и инфраструктура проекта

Именно поэтому React часто называют не "полной платформой", а библиотекой, вокруг которой строится экосистема.

### Чем React хорош

- удобная композиция интерфейса из компонентов
- переиспользование UI-логики
- предсказуемый поток данных сверху вниз
- хорошая экосистема
- удобная работа с динамическими интерфейсами

### Где React особенно полезен

- сложные интерфейсы с большим количеством состояний
- личные кабинеты
- админки
- SPA
- интерактивные формы
- интерфейсы, где данные часто меняются

### Что важно не перепутать

React это не:

- шаблонизатор в чистом виде
- CSS-фреймворк
- библиотека для запросов
- роутер
- state manager

Он может работать вместе со всем этим, но сам по себе не заменяет эти вещи полностью.

**Кратко:**
React это библиотека для построения UI из компонентов. Он отлично подходит для динамических интерфейсов, но полноценное приложение обычно собирается вокруг него из нескольких инструментов.

### Типичные ошибки

- Думать, что React это "полный фреймворк из коробки".
- Ожидать, что React сам решит роутинг, запросы, формы и архитектуру без дополнительных решений.
- Считать React заменой обычному JavaScript, а не библиотекой поверх него.

## SPA, CSR, SSR и что здесь реально происходит

В исходных заметках правильно подмечена связь React со SPA, но тут важно навести порядок в терминах.

### SPA

SPA, или Single Page Application, это приложение, где после первой загрузки пользователь в основном взаимодействует с одной HTML-страницей, а дальнейшие изменения интерфейса происходят уже на клиенте через JavaScript.

Это не означает, что в приложении буквально одна визуальная страница. Страниц с точки зрения пользователя может быть много, но с точки зрения загрузки документа браузер обычно не делает полный переход каждый раз.

### CSR

CSR, или Client-Side Rendering, это подход, когда основная отрисовка интерфейса происходит в браузере.

Это очень частый сценарий для React-приложений.

### SSR

SSR, или Server-Side Rendering, это подход, когда HTML рендерится на сервере и отправляется в браузер уже в готовом или частично готовом виде.

React сам по себе умеет рендериться на сервере, но на практике SSR чаще используют через фреймворки или инфраструктурные решения вроде Next.js.

### Изоморфные и универсальные приложения

В старой терминологии часто говорили "изоморфные" приложения. Сейчас чаще используют слово "универсальные". Смысл в том, что часть React-кода может работать и на сервере, и на клиенте.

Важно

Фраза "весь код в одном месте и нет деления сервер-клиент" неточная. Деление всё равно есть:

- есть клиентская часть
- есть серверная часть
- просто часть логики и компонентов можно переиспользовать между ними

### Плюсы SPA / CSR

- быстрые переходы внутри приложения
- не нужно перезагружать страницу целиком
- удобная работа с локальным состоянием интерфейса
- ощущение более "живого" UI

### Минусы SPA / CSR

- первый бандл может быть тяжёлым
- SEO требует отдельного внимания
- время до полной интерактивности может быть заметным
- приложение сильнее зависит от JavaScript на клиенте

### Когда SSR помогает

- если важен SEO
- если нужен быстрый первый показ контента
- если сеть у пользователя медленная
- если приложение тяжёлое и клиенту невыгодно всё рендерить с нуля

💡 Совет

Не надо думать "SSR лучше CSR" или наоборот. Это не религия, а инженерный выбор под задачу.

**Кратко:**
React часто используют в SPA с клиентским рендерингом, но это не единственный сценарий. При необходимости React можно использовать и с SSR, и в универсальных приложениях.

### Типичные ошибки

- Считать, что React всегда равен SPA.
- Путать SPA и CSR как абсолютные синонимы.
- Описывать SSR как "в React всё в одном месте и сервер-клиент не разделены".
- Думать, что SSR нужен вообще каждому React-проекту.

## Как React обновляет интерфейс

Одна из главных идей React: интерфейс описывается как функция от данных.

То есть не "вручную найди элемент, измени текст, добавь класс, обнови атрибут", а:

- есть состояние
- есть props
- есть компонент
- React сам пересчитывает, что должно быть на экране

### Virtual DOM простыми словами

Virtual DOM это не "вторая настоящая DOM-страница в памяти", как это иногда упрощённо объясняют. Полезнее думать так:

React строит внутреннее описание того, каким интерфейс должен быть после очередного рендера, сравнивает его с предыдущим описанием и потом обновляет реальные DOM-узлы там, где это действительно нужно.

То есть идея не в том, что React вообще не трогает реальный DOM, а в том, что он старается обновлять его осмысленно.

### Что вызывает повторный рендер

В современных React-приложениях компонент обычно перерендеривается, когда:

- изменился его state
- изменились его props
- изменился используемый им context
- перерендерился родитель, и React повторно вызвал дочерний компонент

### Важный нюанс

Повторный рендер компонента не означает, что React обязательно заново "перестроил весь экран". Перерендер это в первую очередь повторный вызов компонента и пересчёт JSX. Дальше React уже решает, какие реальные изменения в DOM действительно нужны.

### Почему это важно понимать

Если не различать:

- рендер компонента
- обновление реального DOM

то очень легко начать преждевременно "оптимизировать" не то место.

**Кратко:**
React не обновляет весь DOM вслепую при каждом изменении. Он пересчитывает UI по данным и применяет реальные изменения там, где это действительно нужно.

### Типичные ошибки

- Думать, что любой ререндер равен полной перерисовке всей страницы.
- Считать Virtual DOM магией, которая автоматически делает всё быстрым.
- Оптимизировать рендеры до того, как появилась реальная проблема.

## Компоненты

Компоненты это базовые строительные блоки React.

Именно вокруг компонентов в React строится почти всё:

- разметка
- поведение
- локальное состояние
- композиция интерфейса

Если упростить, компонент это функция, которая получает входные данные и возвращает описание интерфейса.

### Почему компоненты удобны

- можно переиспользовать
- можно разбивать интерфейс на логические части
- проще поддерживать
- проще тестировать

### Иерархия компонентов

React-приложение обычно выглядит как дерево компонентов:

- есть корневой компонент
- внутри него лежат дочерние
- внутри дочерних свои дочерние

Это не особенность только React, но в React такая композиция особенно важна.

### Функциональные компоненты

Сегодня это основной подход.

```jsx
function HelloWorld() {
  return <h1>Hello world</h1>;
}
```

Или так:

```jsx
export default function HelloWorld() {
  return <h1>Hello world</h1>;
}
```

### Классовые компоненты

Они до сих пор существуют и встречаются в старых проектах, но в новом коде обычно пишут функциональные компоненты.

```jsx
import { Component } from 'react';

class HelloWorld extends Component {
  render() {
    return <h1>Hello world</h1>;
  }
}
```

### Когда классовые компоненты ещё встречаются

- в legacy-проектах
- в старых статьях и курсах
- в коде с Error Boundaries

### Что важно помнить про классы

- Hooks в классовых компонентах не работают
- доступ к `props` идёт через `this.props`
- состояние хранится в `this.state`
- обновление состояния идёт через `this.setState()`

### Про "встроенные компоненты"

Полезно уточнить формулировку. React не поставляет "большую библиотеку UI-компонентов" из коробки по типу готового набора карточек, таблиц и модалок. Но в JSX вы работаете с:

- обычными HTML-тегами вроде `div`, `button`, `input`
- своими пользовательскими компонентами

### Именование компонентов

Пользовательские компоненты пишутся с большой буквы:

```jsx
function PostList() {
  return <div>Posts</div>;
}
```

Если написать с маленькой буквы, React будет считать это HTML-тегом.

### `className`, а не `class`

В JSX для CSS-классов используется `className`:

```jsx
function Button() {
  return <button className="button">Click</button>;
}
```

### Компонент не обязан иметь state

Это важная поправка к исходным заметкам. Не каждый компонент обязан иметь своё состояние. Очень часто компонент вообще:

- получает props
- просто отображает UI
- не хранит локальное состояние

И это нормально.

**Кратко:**
Компоненты это основа React. Сегодня основной стиль это функциональные компоненты, а классовые нужны в основном для legacy-кода и отдельных сценариев.

### Типичные ошибки

- Считать, что каждый компонент обязан иметь state.
- Писать пользовательский компонент с маленькой буквы.
- Использовать `class` вместо `className` в JSX.
- Продолжать писать новые классовые компоненты без реальной причины.

## JSX

JSX это синтаксическая надстройка, которая позволяет писать разметку прямо внутри JavaScript.

Выглядит это как HTML, но это не HTML в чистом виде.

Под капотом JSX превращается в вызовы React API.

### Пример

```jsx
function Card({ title }) {
  return (
    <article className="card">
      <h2>{title}</h2>
    </article>
  );
}
```

### Что важно помнить про JSX

- это JavaScript-выражения плюс специальный синтаксис
- внутри JSX можно вставлять выражения через фигурные скобки
- JSX должен быть корректно вложен
- компонент должен возвращать один корневой узел или Fragment

### Один корневой элемент

Неправильно:

```jsx
function Example() {
  return (
    <h1>Hello</h1>
    <p>World</p>
  );
}
```

Правильно:

```jsx
function Example() {
  return (
    <>
      <h1>Hello</h1>
      <p>World</p>
    </>
  );
}
```

### JavaScript внутри JSX

```jsx
function UserCard({ user }) {
  return (
    <div>
      <h2>{user.name}</h2>
      <p>{user.age} years old</p>
    </div>
  );
}
```

### Атрибуты в JSX

Некоторые имена отличаются от HTML:

- `class` -> `className`
- `for` -> `htmlFor`
- события пишутся в camelCase: `onClick`, `onChange`

### Inline styles

```jsx
function Box() {
  return (
    <div
      style={{
        backgroundColor: 'tomato',
        padding: '12px',
      }}
    >
      Content
    </div>
  );
}
```

Здесь передаётся объект, а не строка как в обычном HTML.

### JSX и `React.createElement`

Смысл исходной заметки верный: JSX преобразуется в вызовы React API. Но в повседневной работе лучше думать не о механике трансформации, а о том, что JSX это удобный способ описывать UI декларативно.

**Кратко:**
JSX это удобный синтаксис для описания интерфейса в React. Он похож на HTML, но живёт внутри JavaScript и подчиняется его правилам.

### Типичные ошибки

- Забывать про один корневой элемент.
- Использовать HTML-атрибуты в старом виде вместо JSX-версий.
- Пытаться вставлять инструкции JavaScript, а не выражения, прямо внутрь JSX.
- Путать inline style-объект со строкой CSS.

## Props

Props это входные данные компонента.

Они передаются сверху вниз:

- родитель передаёт props ребёнку
- ребёнок может передать данные дальше своим детям

Это и есть однонаправленный поток данных.

### Пример

```jsx
function Post({ title, body }) {
  return (
    <article>
      <h2>{title}</h2>
      <p>{body}</p>
    </article>
  );
}

export default function App() {
  return <Post title="React" body="Props example" />;
}
```

### Props только для чтения

Компонент не должен изменять свои props.

Идея такая:

- props приходят извне
- компонент их использует
- изменять их должен тот, кто ими владеет

### `children`

Специальный props `children` позволяет передавать содержимое между открывающим и закрывающим тегом компонента.

```jsx
function Card({ children }) {
  return <div className="card">{children}</div>;
}

export default function App() {
  return (
    <Card>
      <h2>Title</h2>
      <p>Some text</p>
    </Card>
  );
}
```

### Проброс props через много уровней

Если нужно передать данные от верхнего компонента глубоко вниз по дереву, можно столкнуться с prop drilling. Это не ошибка само по себе, но сигнал, что возможно:

- стоит пересобрать дерево компонентов
- нужен Context
- или данные лежат не на том уровне

### Как ребёнок "передаёт" данные родителю

На самом деле ребёнок не отправляет данные напрямую наверх магически. Обычно родитель передаёт вниз callback, а ребёнок его вызывает.

```jsx
import { useState } from 'react';

function PostForm({ onCreate }) {
  function handleSubmit() {
    onCreate({
      id: Date.now(),
      title: 'New post',
    });
  }

  return <button onClick={handleSubmit}>Create post</button>;
}

export default function App() {
  const [posts, setPosts] = useState([]);

  function createPost(newPost) {
    setPosts((prevPosts) => [...prevPosts, newPost]);
  }

  return <PostForm onCreate={createPost} />;
}
```

Здесь данные обновляются в родителе, просто ребёнок помогает запустить это обновление.

**Кратко:**
Props это входные данные компонента. Они идут сверху вниз, не должны изменяться внутри компонента и часто используются вместе с callback-функциями и `children`.

### Типичные ошибки

- Менять props внутри компонента.
- Пытаться "передать данные вверх" без callback от родителя.
- Злоупотреблять prop drilling там, где уже нужен Context или другая структура.

## State

State это внутренние данные компонента, которые могут меняться со временем и влияют на его рендер.

Если props это "что компоненту дали", то state это "что компонент хранит у себя".

### Когда нужен state

- открыта или закрыта модалка
- что введено в поле
- выбранный таб
- список элементов после действий пользователя
- локальный флаг загрузки

### Когда state не нужен

Если значение:

- можно вычислить из props
- можно вычислить из другого state
- не влияет на UI

то отдельный state часто не нужен.

### `useState`

```jsx
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
}
```

### Почему нельзя менять state напрямую

Неправильно:

```jsx
count = count + 1;
```

Правильно:

```jsx
setCount((prevCount) => prevCount + 1);
```

React должен понимать, что состояние изменилось. Именно setter сообщает React о необходимости нового рендера.

### Почему полезна функциональная форма обновления

```jsx
setCount((prevCount) => prevCount + 1);
```

Этот вариант особенно надёжен, когда новое значение зависит от предыдущего.

### Подъём состояния

Если несколько компонентов должны работать с одними и теми же данными, состояние часто поднимают в их ближайшего общего родителя.

Это одна из самых важных практик в React.

**Кратко:**
State нужен для данных, которые меняются и влияют на UI. В функциональных компонентах чаще всего он создаётся через `useState`.

### Типичные ошибки

- Создавать state для значений, которые можно просто вычислить.
- Менять state напрямую.
- Хранить одно и то же значение сразу в нескольких местах без необходимости.
- Не использовать функциональное обновление там, где новое состояние зависит от предыдущего.

## Hooks

Hooks это функции React, которые дают функциональным компонентам доступ к возможностям вроде состояния, эффектов, refs и reducer-логики.

### Правила Hooks

Hooks нужно вызывать:

- только на верхнем уровне компонента
- только внутри функционального компонента
- или внутри собственного custom hook

Нельзя:

- в условиях
- в циклах
- во вложенных функциях
- в обычных функциях вне React-компонента

Это очень важное правило, потому что React опирается на порядок вызова Hooks.

**Кратко:**
Hooks это основной современный способ работать с логикой в функциональных компонентах. Но у них есть строгие правила вызова.

### Типичные ошибки

- Вызывать Hooks внутри `if`.
- Вызывать Hooks внутри обработчиков или вложенных функций.
- Путать custom hook с обычной утилитой.

## `useEffect`

`useEffect` нужен для синхронизации компонента с внешним миром.

Это важная формулировка. Не "для любого кода после рендера", а именно для работы с вещами вне чистого расчёта JSX:

- подписки
- таймеры
- запросы
- ручная работа с API браузера
- интеграции со сторонними библиотеками

### Базовый пример

```jsx
import { useEffect, useState } from 'react';

export default function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds((prev) => prev + 1);
    }, 1000);

    return () => {
      clearInterval(id);
    };
  }, []);

  return <p>{seconds}</p>;
}
```

### Что означает массив зависимостей

- `[]` — эффект после монтирования
- `[value]` — эффект после монтирования и при изменении `value`
- без массива — после каждого рендера

Но это полезно понимать не как магию, а как описание того, от каких значений зависит логика эффекта.

### Cleanup

Если эффект что-то подписывает, запускает или открывает, часто нужен cleanup:

- очистить таймер
- отписаться от события
- остановить подписку

### Важная мысль

`useEffect` не нужен для всего подряд. Если значение можно просто вычислить во время рендера, часто эффект не нужен.

Это один из самых частых источников перегруженного React-кода.

**Кратко:**
`useEffect` нужен для побочных эффектов и синхронизации с внешним миром. Его не стоит использовать там, где достаточно обычного вычисления.

### Типичные ошибки

- Использовать `useEffect` вместо обычной вычисляемой логики.
- Забывать cleanup.
- Неправильно указывать зависимости.
- Создавать лишние эффекты, которые только усложняют компонент.

## `useRef`

`useRef` даёт объект с полем `current`, значение которого можно сохранять между рендерами без запуска нового рендера.

### Два частых применения

1. Получить доступ к DOM-элементу.
2. Хранить изменяемое значение, которое не должно вызывать ререндер.

### Пример доступа к DOM

```jsx
import { useRef } from 'react';

export default function InputFocus() {
  const inputRef = useRef(null);

  function handleFocus() {
    inputRef.current?.focus();
  }

  return (
    <>
      <input ref={inputRef} />
      <button onClick={handleFocus}>Focus</button>
    </>
  );
}
```

### Когда `useRef` не должен заменять state

Если значение должно отображаться в интерфейсе и при изменении обновлять UI, это обычно state, а не ref.

Важно

Прямое изменение DOM в React обычно стараются минимизировать. Но `ref` остаётся нормальным инструментом для фокуса, измерений, интеграции со сторонними библиотеками и похожих задач.

**Кратко:**
`useRef` полезен для доступа к DOM и хранения изменяемых значений без ререндера. Это не замена `useState`.

### Типичные ошибки

- Хранить в `ref` данные, от которых должен обновляться UI.
- Злоупотреблять ручным изменением DOM.
- Пытаться решать `ref`-ами то, что лучше выразить через props и state.

## `useReducer`

`useReducer` это альтернатива `useState`, которая особенно полезна, когда логика обновления состояния становится сложной.

### Когда он особенно полезен

- состояние составное
- много переходов между состояниями
- есть разные типы действий
- хочется явно отделить "что произошло" от "как меняется состояние"

### Пример

```jsx
import { useReducer } from 'react';

const initialState = { count: 0 };

function reducer(state, action) {
  switch (action.type) {
    case 'increment':
      return { count: state.count + 1 };
    case 'decrement':
      return { count: state.count - 1 };
    default:
      return state;
  }
}

export default function Counter() {
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    <div>
      <p>Count: {state.count}</p>
      <button onClick={() => dispatch({ type: 'increment' })}>+</button>
      <button onClick={() => dispatch({ type: 'decrement' })}>-</button>
    </div>
  );
}
```

### Чем он концептуально хорош

`useReducer` делает обновления состояния более явными:

- есть `state`
- есть `action`
- есть `reducer`

Такой код часто легче поддерживать, когда компонент растёт.

**Кратко:**
`useReducer` особенно удобен для сложного состояния и явной логики переходов между состояниями.

### Типичные ошибки

- Использовать `useReducer` там, где хватает простого `useState`.
- Писать reducer с побочными эффектами.
- Возвращать неполное или сломанное состояние из reducer.

## `useLayoutEffect`

`useLayoutEffect` похож на `useEffect`, но запускается синхронно после изменений DOM и до того, как браузер успеет отрисовать экран.

### Когда он нужен

- измерение DOM
- синхронная корректировка layout
- задачи, где важно не допустить визуального "мигания"

### Пример

```jsx
import { useLayoutEffect, useRef, useState } from 'react';

export default function MeasureBox() {
  const boxRef = useRef(null);
  const [width, setWidth] = useState(0);

  useLayoutEffect(() => {
    setWidth(boxRef.current?.offsetWidth ?? 0);
  }, []);

  return (
    <div>
      <div ref={boxRef}>Box</div>
      <p>Width: {width}</p>
    </div>
  );
}
```

### Когда не нужен

Во всех обычных случаях, где подходит `useEffect`, лучше брать `useEffect`. `useLayoutEffect` тяжелее и нужен только там, где важен точный момент между изменением DOM и отрисовкой.

**Кратко:**
`useLayoutEffect` нужен редко и в основном для задач, связанных с layout и измерением DOM до показа пользователю.

### Типичные ошибки

- Использовать `useLayoutEffect` по привычке вместо `useEffect`.
- Засовывать туда тяжёлую работу.
- Не понимать, что он блокирует отрисовку сильнее, чем обычный эффект.

## Оптимизация рендеров: `memo`, `useMemo`, `useCallback`

Оптимизация в React нужна не всегда. Но понимать инструменты важно.

### `memo`

`memo` оборачивает компонент и позволяет React пропускать его повторный рендер, если props не изменились.

```jsx
import { memo } from 'react';

const Item = memo(function Item({ title }) {
  return <li>{title}</li>;
});
```

### `useMemo`

`useMemo` помогает мемоизировать результат вычисления.

```jsx
import { useMemo } from 'react';

function List({ items }) {
  const sortedItems = useMemo(() => {
    return [...items].sort((a, b) => a.localeCompare(b));
  }, [items]);

  return (
    <ul>
      {sortedItems.map((item) => (
        <li key={item}>{item}</li>
      ))}
    </ul>
  );
}
```

### `useCallback`

`useCallback` мемоизирует саму функцию.

```jsx
import { useCallback, useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  const increment = useCallback(() => {
    setCount((prev) => prev + 1);
  }, []);

  return <button onClick={increment}>{count}</button>;
}
```

### Важная мысль

Эти инструменты нужны не "чтобы было профессионально", а только когда есть конкретная причина:

- дорогое вычисление
- чувствительный дочерний компонент
- проблема с лишними рендерами действительно подтверждена

### Про исходную заметку о `React.memo`

Там идея верная, но слово "хешировать" здесь неудачное. Правильнее говорить "мемоизировать" или "пропускать лишний ререндер при неизменных props".

**Кратко:**
`memo`, `useMemo` и `useCallback` помогают уменьшать лишнюю работу, но применять их стоит осознанно, а не автоматически.

### Типичные ошибки

- Мемоизировать всё подряд.
- Использовать `useMemo` там, где вычисление дешёвое.
- Ожидать, что `memo` спасёт компонент, если props всё равно постоянно создаются заново.

## HOC

HOC, или Higher-Order Component, это функция, которая принимает компонент и возвращает новый компонент.

### Зачем они были нужны

Исторически HOC использовали для:

- переиспользования логики
- оборачивания компонентов дополнительным поведением
- авторизации
- логирования
- подписок и данных

### Пример

```jsx
function withLogger(WrappedComponent) {
  return function LoggedComponent(props) {
    console.log(`Render: ${WrappedComponent.name}`);
    return <WrappedComponent {...props} />;
  };
}
```

### Современный взгляд

Сегодня во многих случаях HOC вытеснены:

- custom hooks
- композиция компонентов
- render props в отдельных сценариях

Но знать HOC полезно, потому что в старом коде они встречаются очень часто.

**Кратко:**
HOC это исторически важный паттерн React для переиспользования логики. В новом коде чаще выбирают custom hooks и композицию, но HOC всё ещё нужно уметь читать.

### Типичные ошибки

- Использовать HOC там, где проще custom hook.
- Терять props при оборачивании компонента.
- Слишком глубоко вкладывать HOC и усложнять дерево компонентов.

## Error Boundaries

Error Boundary это специальный компонент, который позволяет перехватывать ошибки рендера в дочернем дереве и показывать запасной UI вместо падения всей части интерфейса.

### Очень важная поправка

Официально Error Boundaries в React реализуются через **классовые компоненты**.

То есть сам React не даёт встроенный Hook для нативного определения Error Boundary в функциональном компоненте. Если вы видите `useErrorBoundary`, это обычно решение из сторонней библиотеки, а не core React API.

### Пример

```jsx
import React from 'react';

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    console.error('Caught error:', error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;
    }

    return this.props.children;
  }
}
```

### Что Error Boundary ловит

Он ловит ошибки:

- при рендере
- в lifecycle-методах
- в конструкторе дочерних компонентов

### Что он не ловит

- ошибки в event handlers
- ошибки в асинхронных колбэках
- ошибки на сервере при SSR
- ошибки внутри самого boundary

**Кратко:**
Error Boundaries нужны для безопасной деградации UI при ошибках рендера. В официальном React они реализуются через классовые компоненты.

### Типичные ошибки

- Считать, что Error Boundary ловит вообще любые ошибки приложения.
- Называть сторонние hooks нативной возможностью React.
- Ожидать, что boundary заменит нормальную обработку ошибок в запросах и событиях.

## `lazy` и разделение кода

Если компонент большой или используется не сразу, его можно подгружать лениво.

### `React.lazy`

```jsx
import { Suspense, lazy } from 'react';

const SettingsPage = lazy(() => import('./SettingsPage.js'));

export default function App() {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <SettingsPage />
    </Suspense>
  );
}
```

### Что это даёт

- уменьшает размер начального бандла
- позволяет грузить тяжёлые части приложения позже
- помогает ускорить первую загрузку

### Важная мысль

Ленивая загрузка это не волшебная кнопка "ускорить всё". Она помогает именно тогда, когда есть смысл отложить загрузку части кода до реального использования.

**Кратко:**
`lazy` и `Suspense` позволяют подгружать компоненты по требованию и уменьшать нагрузку на стартовую загрузку приложения.

### Типичные ошибки

- Оборачивать в lazy всё подряд.
- Забывать `Suspense`.
- Делать lazy для компонентов, которые всё равно нужны сразу на первом экране.

## Стили в React

React не навязывает единственный способ стилизации.

### Частые варианты

- обычные CSS-файлы
- CSS Modules
- inline styles
- CSS-in-JS решения
- CSS-переменные

### CSS Modules

Это хороший способ изолировать стили компонента.

```css
/* Button.module.css */
.button {
  padding: 8px 12px;
}
```

```jsx
import styles from './Button.module.css';

export default function Button() {
  return <button className={styles.button}>Click</button>;
}
```

### Inline styles

Удобны для:

- динамических значений
- быстрых локальных стилей

Но неудобны как единственный основной способ стилизации большого приложения.

### Практический выбор

Для большинства обычных проектов CSS Modules или хорошо организованный обычный CSS часто дают очень хороший баланс простоты и контроля.

**Кратко:**
В React можно стилизовать компоненты разными способами. На практике чаще всего выбирают подход, который даёт нормальную изоляцию и не усложняет проект без причины.

### Типичные ошибки

- Использовать только inline styles для всего проекта.
- Делать сложную стилизацию без понятной системы.
- Не отделять стили компонента от глобальных стилей, когда это уже начинает мешать.

## Инструменты вокруг React

Сам React это только часть стека. Вокруг него обычно живут и другие инструменты.

### Сборка

Исторически часто встречались:

- webpack
- rollup
- parcel

Сегодня в современных проектах часто используют и более новые инструменты, например Vite как dev/build-решение.

### Транспиляция

Babel исторически отвечал за преобразование современного JavaScript и JSX в код, который понятен окружению сборки и браузерам.

### Типизация

Сегодня чаще всего это TypeScript.

### Роутинг

Для клиентского роутинга в React обычно используют библиотеку вроде React Router.

### Работа с данными

Здесь возможны разные подходы:

- `fetch`
- `axios`
- клиенты для GraphQL
- библиотеки для серверного состояния

### State management

Когда локального состояния и Context уже недостаточно, могут появиться:

- Redux
- MobX
- Zustand
- другие решения

### Тестирование

Часто используются:

- Jest
- Testing Library
- Vitest в некоторых проектах

### Линтинг и качество кода

- ESLint
- Prettier

### Важная мысль

Не нужно пытаться включить в проект весь стек сразу. Сначала нужен только минимум, а остальное добавляется по реальной необходимости.

**Кратко:**
React почти всегда живёт внутри более широкого стека. Но этот стек должен расти по мере сложности проекта, а не потому что "так у всех".

### Типичные ошибки

- Собирать перегруженный стек для маленького проекта.
- Подключать state manager заранее "на всякий случай".
- Слепо копировать стек из чужого проекта без понимания, зачем он там.

## Что особенно важно унести с собой

Если убрать детали, фундамент React держится на нескольких ключевых идеях:

- UI состоит из компонентов
- данные в основном текут сверху вниз
- props приходят извне, state живёт внутри
- JSX это удобный синтаксис для описания интерфейса
- Hooks дают компонентам современную логику состояния и эффектов
- лишняя оптимизация не нужна, пока нет реальной проблемы

Если эти вещи уложены в голове, React перестаёт быть "магией из JSX" и становится просто удобной моделью построения интерфейса.

**Кратко:**
Главное в React не в большом количестве API, а в понимании компонентов, потока данных, state, props и рендера.

## Куда идти дальше

После этого конспекта логично двигаться так:

1. Научиться уверенно писать простые компоненты, формы и списки.
2. Отдельно закрепить `useState`, `useEffect`, `useRef`.
3. Поднять маленькое SPA с роутингом и запросами.
4. Разобраться с формами, асинхронными данными и обработкой ошибок.
5. Только потом добавлять более тяжёлые вещи вроде глобального state management или SSR.

💡 Совет

Лучший способ закрепить React это не перечитывать теорию по кругу, а сделать 2-3 маленьких проекта:

- список задач
- поиск с фильтрами
- небольшую админку
- мини-магазин

**Кратко:**
React лучше всего понимается руками: через компоненты, списки, формы, запросы и реальные перерисовки интерфейса.
