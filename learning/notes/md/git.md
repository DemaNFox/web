# Git

## Что такое Git

Git это распределенная система контроля версий.

Если говорить просто, Git помогает:

- отслеживать изменения в проекте
- возвращаться к прошлым версиям
- работать в команде без постоянного хаоса
- вести разработку через ветки
- безопаснее экспериментировать с кодом

То есть Git нужен не только для "сохранить код". Его основная ценность в том, что он хранит историю изменений и позволяет этой историей управлять.

### Git и GitHub это не одно и то же

Это одна из самых частых путаниц.

`Git` это инструмент контроля версий.

`GitHub` это сервис для хранения Git-репозиториев и совместной работы.

Проще так:

- Git это сама система
- GitHub это один из популярных хостингов для Git-репозиториев

Кроме GitHub есть и другие сервисы:

- GitLab
- Bitbucket
- Azure DevOps

### Почему Git так полезен

Без Git разработка быстро превращается в набор файлов вроде:

- `project-final`
- `project-final-2`
- `project-final-real`

Git убирает этот хаос. Вместо этого у тебя есть:

- история коммитов
- понятные точки изменений
- ветки для новых задач
- возможность сравнивать версии
- механизмы отката

### Кратко:

- Git это система контроля версий.
- Он хранит историю проекта и помогает управлять изменениями.
- Git и GitHub это разные вещи: инструмент и сервис.

### Типичные ошибки

- Путать Git и GitHub как будто это одно и то же.
- Воспринимать Git только как "облако для кода".
- Работать без веток и истории, как будто Git это просто кнопка "сохранить".

## Как Git думает о проекте

Чтобы Git был понятным, полезно смотреть на него не как на магию, а как на систему из нескольких областей.

В Git обычно выделяют три главные зоны:

- рабочая директория
- индекс, или staging area
- репозиторий

### Рабочая директория

Это твои обычные файлы в проекте, которые ты редактируешь прямо сейчас.

### Индекс

Индекс, или staging area, это промежуточная область перед коммитом.

Туда попадают изменения после `git add`.

То есть `git add` не делает коммит. Он говорит Git:

"вот эти изменения я хочу включить в следующий коммит"

### Репозиторий

Это уже сохраненная история коммитов.

Когда ты делаешь `git commit`, Git берет то, что лежит в индексе, и записывает это как новый коммит в историю.

### Простая схема

Поток обычно такой:

1. меняешь файлы в рабочей директории
2. добавляешь нужные изменения в индекс через `git add`
3. сохраняешь их в историю через `git commit`

### Почему staging area важна

Новички часто думают, что Git работает по схеме:

"изменил файл -> сразу коммит"

Но на практике staging area очень удобна, потому что позволяет:

- коммитить только часть изменений
- собирать логически чистые коммиты
- не тащить в коммит случайные правки

### Кратко:

- Рабочая директория это текущие измененные файлы.
- Индекс это подготовленные к коммиту изменения.
- Репозиторий это уже сохраненная история.

### Типичные ошибки

- Думать, что `git add` уже создает коммит.
- Коммитить все подряд без staging area как смыслового фильтра.
- Не понимать, почему в коммит попала не вся рабочая директория, а только часть.

## Состояния файлов в Git

Git отслеживает состояние файлов.

В упрощенном виде чаще всего встречаются такие состояния:

- `untracked`
- `modified`
- `staged`
- `unmodified`

### Untracked

Git видит файл, но еще не отслеживает его.

Например, ты создал новый файл, но еще не делал `git add`.

### Modified

Файл уже отслеживается Git, но был изменен после последнего коммита.

### Staged

Изменения файла добавлены в индекс и готовы попасть в следующий коммит.

### Unmodified

Файл отслеживается и не содержит новых изменений.

### Как посмотреть состояние

```bash
git status
```

Это одна из самых важных команд в Git.

Она показывает:

- какие файлы изменены
- какие лежат в staging area
- какие не отслеживаются
- на какой ветке ты находишься

### Кратко:

- Git видит, в каком состоянии находится каждый файл.
- `git status` это базовая команда для понимания текущей картины.
- Состояние файла влияет на то, попадет ли он в коммит.

### Типичные ошибки

- Не смотреть `git status` перед коммитом.
- Путать `modified` и `staged`.
- Удивляться, что новый файл не попал в коммит без `git add`.

## Первая настройка Git

Перед нормальной работой Git обычно настраивают имя и email автора.

```bash
git config --global user.name "Nick"
git config --global user.email "nick@example.com"
```

Эти данные Git использует в коммитах.

### Проверка настроек

```bash
git config --list
```

При желании можно смотреть и конкретные значения:

```bash
git config user.name
git config user.email
```

### Global и local

`--global` означает, что настройка применяется ко всем репозиториям текущего пользователя.

Но конфигурацию можно задавать и локально внутри одного проекта, без `--global`.

Это полезно, если:

- в разных проектах нужны разные данные
- используется рабочий и личный аккаунт

### Кратко:

- Перед работой с Git обычно задают `user.name` и `user.email`.
- `--global` применяет настройку для всех репозиториев пользователя.
- Локальная конфигурация может переопределять глобальную.

### Типичные ошибки

- Не настроить имя и email перед первыми коммитами.
- Путать глобальные и локальные настройки.
- Коммитить с неверным email в рабочий репозиторий.

## Создание репозитория и базовый рабочий цикл

### Инициализация репозитория

Чтобы создать Git-репозиторий в текущей папке:

```bash
git init
```

После этого Git начинает хранить служебные данные в папке `.git`.

### Добавление файлов в индекс

```bash
git add file.txt
```

Или:

```bash
git add .
```

Важно понимать: `git add .` добавляет изменения из текущей директории и вложенных путей, но привычка blindly использовать эту команду опасна. Часто лучше добавлять файлы осознанно.

### Создание коммита

```bash
git commit -m "Initial project version"
```

Коммит сохраняет состояние проиндексированных изменений.

### Полный минимальный цикл

```bash
git init
git status
git add .
git commit -m "Initial commit"
```

### Что такое коммит

Коммит это не просто "снимок файлов". Если говорить точнее, коммит хранит ссылку на дерево состояния проекта, метаданные автора, дату, сообщение и ссылки на родительские коммиты.

Но для практики полезно держать простую модель:

**Коммит это зафиксированная точка истории проекта.**

### Как писать сообщения коммитов

Сообщение должно отвечать на вопрос:

"что изменено?"

Нормально:

- `Add user login validation`
- `Fix cart total calculation`
- `Update README with setup steps`

Слабо:

- `fix`
- `changes`
- `update`

### Кратко:

- `git init` создает репозиторий.
- `git add` подготавливает изменения к коммиту.
- `git commit` сохраняет их в историю.
- Сильный коммит это маленькое логичное изменение с понятным сообщением.

### Типичные ошибки

- Коммитить слишком большие и разнородные изменения одним коммитом.
- Бездумно использовать `git add .`.
- Писать бессмысленные сообщения коммитов.

## Просмотр истории и состояния

### git status

```bash
git status
```

Показывает текущее состояние рабочей директории и индекса.

### git log

```bash
git log
```

Показывает историю коммитов.

Часто удобнее использовать:

```bash
git log --oneline --graph --decorate
```

Это дает более компактный и читаемый вид истории.

### git diff

Очень полезная команда для сравнения изменений.

```bash
git diff
```

Показывает изменения, которые есть в рабочей директории, но еще не добавлены в индекс.

```bash
git diff --staged
```

Показывает то, что уже добавлено в индекс и пойдет в следующий коммит.

### Кратко:

- `git status` показывает текущую рабочую картину.
- `git log` показывает историю.
- `git diff` помогает увидеть точные изменения.

### Типичные ошибки

- Коммитить код, не посмотрев `git diff`.
- Смотреть только `git log` и не пользоваться компактными форматами.
- Не различать `git diff` и `git diff --staged`.

## Ветки

Ветка в Git это отдельная линия разработки.

Если говорить проще, ветки позволяют работать над задачами изолированно, не ломая основную линию разработки.

### Зачем нужны ветки

Например:

- в `main` лежит стабильный код
- в отдельной ветке ты делаешь новую фичу
- после завершения работы изменения сливаются обратно

Это намного безопаснее, чем писать все сразу в одной ветке.

### Создание ветки

```bash
git branch feature/auth
```

### Список веток

```bash
git branch
```

### Переход между ветками

Исторически для этого часто использовали `git checkout`:

```bash
git checkout feature/auth
```

Но в современном Git для переключения между ветками обычно рекомендуют `git switch`:

```bash
git switch feature/auth
```

### Создать ветку и сразу перейти в нее

Старый вариант:

```bash
git checkout -b feature/auth
```

Современный вариант:

```bash
git switch -c feature/auth
```

### Переименование ветки

```bash
git branch -m new-name
```

### Удаление ветки

```bash
git branch -d feature/auth
```

Если Git считает, что ветка не слита, он не даст удалить ее через `-d`.

Принудительное удаление:

```bash
git branch -D feature/auth
```

С этим нужно быть осторожным.

### Detached HEAD

Если переключиться не на ветку, а прямо на коммит:

```bash
git switch --detach <commit>
```

ты окажешься в состоянии `detached HEAD`.

Это не ошибка само по себе. Это режим, где можно посмотреть старую версию или провести эксперимент. Но новые коммиты в таком состоянии не будут принадлежать обычной ветке, пока ты не создашь новую ветку вручную.

### Кратко:

- Ветки позволяют изолировать задачи.
- Для переключения сегодня удобнее `git switch`, хотя `git checkout` все еще существует.
- `detached HEAD` полезен для просмотра истории и экспериментов, но с ним нужно понимать контекст.

### Типичные ошибки

- Работать над всеми задачами прямо в `main`.
- Не понимать разницу между веткой и просто checkout на конкретный коммит.
- Случайно делать коммиты в `detached HEAD`.

## Слияние веток: merge

Когда работа в отдельной ветке завершена, ее обычно нужно объединить с другой веткой.

Для этого используют `git merge`.

### Базовый пример

Допустим:

- ты находишься в `main`
- хочешь подтянуть в нее изменения из `feature/auth`

```bash
git switch main
git merge feature/auth
```

Команду `merge` выполняют **из той ветки, в которую хотят влить изменения**.

Это важная мысль.

### Fast-forward merge

Если ветка `main` не менялась после создания `feature/auth`, Git иногда может просто "передвинуть указатель" вперед без отдельного merge-коммита.

Это называется fast-forward merge.

### Merge commit

Если истории веток разошлись, Git создаст отдельный merge commit.

Это нормально и часто ожидаемо.

### Конфликты

Если в двух ветках изменили одни и те же строки, Git не всегда сможет слить изменения автоматически.

Тогда возникает merge conflict.

Обычный сценарий такой:

1. Git сообщает о конфликте
2. ты открываешь файл
3. вручную выбираешь итоговый вариант
4. сохраняешь файл
5. добавляешь исправленный файл через `git add`
6. завершаешь merge

### Прервать merge

Если слияние пошло не туда:

```bash
git merge --abort
```

### Кратко:

- `git merge` объединяет историю одной ветки в другую.
- Команда выполняется из целевой ветки.
- Конфликты нужно разрешать вручную, когда Git не может сделать это сам.

### Типичные ошибки

- Запускать `git merge` не из той ветки.
- Пугаться merge commit как будто это всегда плохо.
- Разрешать конфликты не посмотрев, какой вариант действительно нужен.

## Rebase

`git rebase` тоже используется для объединения истории, но делает это по-другому.

Если очень упрощенно:

- `merge` сохраняет разветвленную историю как есть
- `rebase` переносит коммиты одной ветки поверх другой, переписывая историю

### Пример

```bash
git switch feature/auth
git rebase main
```

Это означает:

- взять коммиты из `feature/auth`
- как будто заново "положить" их поверх актуальной `main`

### Зачем это делают

Rebase часто используют, чтобы:

- сделать историю более линейной
- подтянуть свежую `main` в feature-ветку без merge-коммита

### Очень важное правило

Обычно не стоит делать rebase публичной ветки, которую уже используют другие разработчики.

Причина в том, что rebase переписывает историю. А переписывание общей истории может ломать чужую работу.

### Конфликты при rebase

Конфликты здесь тоже возможны.

После исправления конфликта обычно делают:

```bash
git add .
git rebase --continue
```

Отменить:

```bash
git rebase --abort
```

### merge или rebase

Нет универсального ответа "что всегда лучше".

Практически:

- `merge` проще и безопаснее для понимания истории
- `rebase` делает историю чище, но требует большего понимания

### Кратко:

- `rebase` переносит коммиты поверх другой базы.
- Он переписывает историю.
- Для локальной feature-ветки это часто удобно, для общей опубликованной ветки уже опаснее.

### Типичные ошибки

- Использовать rebase, не понимая, что он переписывает историю.
- Делать rebase публичной ветки без необходимости.
- Путать rebase и merge как будто это одно и то же.

## Reset, revert и restore

Это одна из самых важных и самых путаных тем в Git.

Здесь особенно важно не запоминать команды вслепую, а понимать смысл.

### git revert

`git revert` создает **новый коммит**, который отменяет изменения предыдущего коммита.

```bash
git revert <commit>
```

Это безопасный способ отмены, если коммит уже попал в общую историю.

Почему безопасный:

- история не переписывается
- создается новый явный коммит-отмена

### git reset

`git reset` двигает указатель ветки и может менять индекс и рабочую директорию в зависимости от режима.

Это уже более опасный инструмент, потому что он может фактически "убирать" коммиты из текущей ветки.

#### soft

```bash
git reset --soft HEAD~1
```

Убирает последний коммит, но оставляет изменения в индексе.

#### mixed

```bash
git reset HEAD~1
```

Это режим по умолчанию. Убирает коммит и вынимает изменения из индекса, но оставляет их в рабочей директории.

#### hard

```bash
git reset --hard HEAD~1
```

Убирает коммит и выбрасывает изменения из рабочей директории.

Это уже опасная операция.

### git restore

В современном Git для восстановления файлов чаще используют `git restore`.

Например:

```bash
git restore file.txt
```

Это вернет файл к состоянию из индекса.

А чтобы убрать файл из staging area:

```bash
git restore --staged file.txt
```

### Простое правило

- `revert` лучше, когда нужно безопасно отменить уже сохраненный публичный коммит
- `reset` лучше, когда нужно переписать локальную историю и ты понимаешь последствия
- `restore` лучше, когда нужно восстановить файлы или убрать их из staging

### Кратко:

- `revert` создает новый коммит-отмену.
- `reset` двигает историю и может быть опасным.
- `restore` работает с файлами и staging area.

### Типичные ошибки

- Использовать `reset --hard`, не понимая, что изменения могут пропасть.
- Делать `reset` в общей ветке вместо `revert`.
- Путать отмену коммита и восстановление файла.

## Работа с удаленным репозиторием

Git очень часто используют не только локально, но и вместе с удаленным репозиторием.

### Клонирование

```bash
git clone <url>
```

Git создаст локальную копию репозитория и автоматически добавит удаленный репозиторий с именем `origin`.

### Проверка удаленных репозиториев

```bash
git remote
git remote -v
```

### Добавить удаленный репозиторий вручную

```bash
git remote add origin <url>
```

### Получить изменения с удаленного репозитория

```bash
git fetch
```

`fetch` загружает обновления, но не сливает их в текущую ветку автоматически.

Это безопасная команда для "сначала посмотреть, что там пришло".

### git pull

```bash
git pull
```

`git pull` это, по сути, `fetch` + интеграция изменений в текущую ветку.

Обычно интеграция происходит через merge или rebase, в зависимости от настроек и параметров.

Очень важно: `git pull` **скачивает и применяет изменения из удаленного репозитория к локальной ветке**.

### git push

```bash
git push
```

`git push` делает обратное:

**отправляет локальные коммиты в удаленный репозиторий**.

Это частое место путаницы.

### Первая публикация ветки

```bash
git push -u origin feature/auth
```

Флаг `-u` или `--set-upstream` связывает локальную ветку с удаленной. После этого можно будет чаще использовать просто `git push` и `git pull` без явного указания ветки.

### Посмотреть связь локальной и удаленной ветки

```bash
git branch -vv
```

### Показать все ветки, включая remote-tracking

```bash
git branch -a
```

### Кратко:

- `clone` создает локальную копию репозитория.
- `fetch` загружает изменения без автоматического слияния.
- `pull` получает изменения и интегрирует их в текущую ветку.
- `push` отправляет локальные коммиты в remote.

### Типичные ошибки

- Путать `pull` и `push`.
- Делать `pull`, не понимая, merge это будет или rebase.
- Не настраивать upstream для новой ветки и потом удивляться ошибкам `push`.

## .gitignore

Не все файлы проекта нужно хранить в репозитории.

Для этого используют `.gitignore`.

В этом файле перечисляют пути и шаблоны, которые Git должен игнорировать.

Примеры:

```gitignore
node_modules/
dist/
.env
*.log
```

### Что обычно игнорируют

- зависимости
- собранные артефакты
- временные файлы
- локальные конфиги
- секреты и ключи

### Важный нюанс

`.gitignore` работает для файлов, которые Git еще не начал отслеживать.

Если файл уже попал в репозиторий, просто добавить его в `.gitignore` недостаточно. Сначала нужно убрать его из отслеживания.

### Кратко:

- `.gitignore` указывает Git, какие файлы не нужно отслеживать.
- Обычно туда попадают временные, собранные и секретные файлы.
- Если файл уже отслеживается, одного `.gitignore` недостаточно.

### Типичные ошибки

- Коммитить `.env`, `node_modules` или build-артефакты.
- Думать, что `.gitignore` автоматически перестанет отслеживать уже закоммиченный файл.
- Не проверять, что именно реально попало в индекс.

## Исправление последнего коммита

Иногда ты сделал коммит и потом понял:

- забыл добавить файл
- ошибся в сообщении
- нужно чуть поправить содержимое

Для этого есть `--amend`.

```bash
git add forgotten_file
git commit --amend
```

Если нужно только заменить сообщение:

```bash
git commit --amend -m "New commit message"
```

### Важный нюанс

`--amend` переписывает последний коммит. Если этот коммит уже был отправлен в удаленный репозиторий и его используют другие, нужно быть осторожным.

### Кратко:

- `git commit --amend` изменяет последний коммит.
- Это удобно для мелких исправлений.
- Для уже опубликованных коммитов такая операция требует осторожности.

### Типичные ошибки

- Менять через `--amend` уже опубликованный коммит без понимания последствий.
- Использовать amend для больших переделок вместо нового коммита.
- Не проверять содержимое индекса перед amend.

## Stash

Хотя в исходнике этой темы почти нет, в реальной работе она очень полезна.

`git stash` позволяет временно убрать незакоммиченные изменения, чтобы переключиться на другую задачу.

### Спрятать изменения

```bash
git stash
```

### Посмотреть список stash

```bash
git stash list
```

### Вернуть последние спрятанные изменения

```bash
git stash pop
```

Или применить без удаления из списка:

```bash
git stash apply
```

### Когда stash полезен

- срочно нужно переключиться на другую ветку
- есть незавершенные изменения
- не хочется делать "мусорный" временный коммит

### Кратко:

- `stash` временно убирает незакоммиченные изменения.
- Это удобно для быстрых переключений между задачами.
- `pop` возвращает изменения и убирает их из stash-списка.

### Типичные ошибки

- Злоупотреблять stash вместо нормальных веток и коммитов.
- Забывать, что внутри stash лежат важные незавершенные изменения.
- Не проверять, что именно будет спрятано.

## Практический рабочий сценарий

Ниже типичный нормальный поток работы.

### Новая задача

```bash
git switch main
git pull
git switch -c feature/header-redesign
```

### Работа над кодом

```bash
git status
git diff
git add src/header.js
git commit -m "Redesign header layout"
```

### Подтянуть свежую main в feature-ветку

Вариант через merge:

```bash
git switch feature/header-redesign
git merge main
```

Вариант через rebase:

```bash
git switch feature/header-redesign
git rebase main
```

### Отправка ветки на сервер

```bash
git push -u origin feature/header-redesign
```

### После завершения работы

```bash
git switch main
git pull
git merge feature/header-redesign
git push
```

### Кратко:

- Начинай задачу с отдельной ветки.
- Делай маленькие логичные коммиты.
- Перед слиянием подтягивай свежую базу.
- Отправляй ветки в remote осознанно, а не хаотично.

### Типичные ошибки

- Начинать задачу из устаревшей `main`.
- Держать одну длинную ветку для десятка разных задач.
- Откладывать коммиты до состояния "200 файлов изменено".

## Когда merge, когда rebase, когда revert

Это один из самых частых практических вопросов.

### Когда merge

Используй `merge`, если:

- хочешь сохранить реальную историю ветвления
- нужна максимально безопасная и понятная командная работа
- не хочешь переписывать историю

### Когда rebase

Используй `rebase`, если:

- работаешь в своей локальной feature-ветке
- хочешь линейную и более чистую историю
- понимаешь, что история будет переписана

### Когда revert

Используй `revert`, если:

- нужно отменить уже сохраненный коммит
- особенно если он уже в общей истории

### Когда reset

Используй `reset`, если:

- нужно переписать свою локальную историю
- ты точно понимаешь последствия

### Кратко:

- `merge` безопаснее для общей истории.
- `rebase` чище для локальной работы, но переписывает историю.
- `revert` лучший друг для безопасной отмены уже опубликованных коммитов.

### Типичные ошибки

- Выбирать команду по памяти, а не по смыслу.
- Использовать `reset`, когда нужен `revert`.
- Тащить rebase в командную ветку без согласованного процесса.

## Итог

Git становится заметно проще, если держать в голове несколько базовых идей:

1. есть рабочая директория
2. есть staging area
3. есть история коммитов
4. ветки нужны для изоляции задач
5. remote нужен для совместной работы и хранения репозитория

Все остальное уже строится на этих принципах.

Если запомнить самую практическую мысль, то она будет такой:

**Git не просто хранит код. Он помогает управлять историей изменений так, чтобы разработка оставалась контролируемой.**

### Кратко:

- Git это система контроля версий, а не просто хранилище файлов.
- База Git это `status`, `add`, `commit`, `branch`, `merge`, `pull`, `push`.
- Самые опасные команды это те, которые переписывают историю или выбрасывают изменения.
- Хорошая работа с Git это маленькие коммиты, осознанные ветки и понимание смысла команд.
