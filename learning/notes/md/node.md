# Node.js: структурированный конспект

> Во всех примерах с `import` подразумевается, что проект использует ES Modules, например через `"type": "module"` в `package.json`.

## Что такое Node.js

Node.js это не отдельный язык программирования, а среда выполнения JavaScript вне браузера.

Если коротко, то Node.js отвечает на вопрос:

"Как запускать JavaScript не в окне браузера, а как полноценную программу?"

Проще говоря:

- в браузере JavaScript работает рядом с `window`, DOM и HTML-страницей
- в Node.js JavaScript работает на стороне сервера или просто как отдельная программа
- вместо DOM здесь доступны API для работы с файлами, сетью, процессами и операционной системой

Node.js построен вокруг движка `V8`, который выполняет JavaScript, и `libuv`, которая помогает организовать неблокирующий ввод-вывод и цикл событий.

Если совсем по-человечески, то раньше у JavaScript была очень жёсткая ассоциация: "это язык для браузера". То есть открыл страницу, загрузился код, дальше этот код работает рядом с HTML, CSS и DOM.

Node.js поменял картину. Он дал JavaScript возможность жить отдельно от браузера. Благодаря этому на JavaScript стало можно:

- запускать серверы
- писать скрипты автоматизации
- собирать проекты
- работать с файлами на диске
- поднимать сетевые сервисы

То есть JavaScript из "языка для кнопок на сайте" превратился в полноценный инструмент для бэкенда, инфраструктуры, утилит и серверной логики.

### Чем Node.js отличается от JavaScript в браузере

Сам язык во многом один и тот же: переменные, функции, объекты, классы, массивы, промисы, `async/await` работают знакомо.

Но окружение разное.

В браузере у вас есть:

- `window`
- `document`
- DOM
- события страницы
- вкладки, localStorage, history и так далее

В Node.js этого нет. Зато есть:

- `process`
- файловая система
- сеть
- переменные окружения
- модули Node.js
- доступ к операционной системе

Именно поэтому код для браузера нельзя бездумно копировать в Node.js и наоборот. Язык похожий, но доступные инструменты вокруг разные.

### Где Node.js обычно используют

- серверы и REST API
- CLI-утилиты
- скрипты автоматизации
- real-time приложения
- прокси, стриминг, обработка большого числа соединений
- инструменты фронтенда: сборщики, dev-серверы, линтеры, тест-раннеры

### Где Node.js подходит хуже

Node.js не лучший выбор для тяжёлых CPU-задач, где процессор долго занят вычислениями:

- рендер видео
- сложные научные расчёты
- машинное обучение без специализированной инфраструктуры
- большие синхронные вычисления в основном потоке

Это не значит, что так делать нельзя. Это значит, что без `worker_threads`, очередей или выноса задач в отдельные сервисы приложение быстро упрётся в производительность.

Именно поэтому Node.js особенно ценят там, где приложение постоянно обрабатывает события, соединения, запросы и файлы, а не бесконечно считает что-то тяжёлое в лоб.

**Кратко:**
Node.js это среда выполнения JavaScript вне браузера. Она особенно хороша там, где много ввода-вывода, сети и параллельных запросов, но основной поток лучше не перегружать тяжёлыми вычислениями.

### Типичные ошибки

- Думать, что Node.js и JavaScript это одно и то же.
- Ожидать, что код из браузера с `document` или `window` будет работать в Node.js без изменений.
- Считать Node.js "универсально лучшим" решением вообще для всех задач, включая тяжёлые вычисления.

## Установка и первый запуск

Для практики обычно ставят актуальную **LTS-версию** Node.js с официального сайта.

Почему именно LTS:

- она стабильнее
- под неё лучше всего проверены пакеты
- на ней обычно проще учиться и работать
- в продакшене её используют чаще, чем экспериментальные ветки

Если задача учебная, почти всегда разумно начинать именно с LTS.

После установки полезно проверить, что всё действительно доступно из терминала:

```bash
node -v
npm -v
```

Если обе команды возвращают версии, значит установка прошла нормально.

### Первый файл

```js
// index.js
const sum = 2 + 3;

console.log('Сумма:', sum);
console.log('Hello Node.js');
```

Запуск:

```bash
node index.js
```

Тут важно понять базовую механику:

- `node` запускает среду выполнения
- `index.js` это точка входа
- Node.js читает файл сверху вниз и выполняет код

На старте этого уже достаточно. Не нужно пока усложнять себе жизнь ни сборщиками, ни фреймворками, ни TypeScript.

На этом этапе цель очень простая: убедиться, что среда работает, файлы запускаются, а вы понимаете базовый цикл "написал код -> запустил -> увидел результат".

### REPL Node.js

Если запустить просто:

```bash
node
```

откроется REPL, то есть интерактивный режим, где можно выполнять JavaScript по одной строке.

Полезные команды REPL:

- `.help` показать список служебных команд
- `.save file.js` сохранить текущую сессию в файл
- `.load file.js` загрузить файл в текущую сессию
- `.editor` перейти в многострочный режим
- `.exit` выйти

💡 Совет

REPL удобно использовать для быстрых проверок: как работает метод, что вернёт модуль, какой тип у значения и так далее.

**Кратко:**
После установки проверь `node -v` и `npm -v`. Скрипты запускаются через `node file.js`, а REPL полезен для быстрых экспериментов.

### Типичные ошибки

- Ставить случайную нестабильную версию Node.js для обучения, а потом ловить несовместимости.
- Путать команду `node` с `npm`.
- Не проверять версии после установки и потом тратить время на поиск проблемы в `PATH`.

## Из чего состоит Node.js

Если сильно упростить, внутри есть несколько основных частей:

Здесь важно не просто запомнить список частей, а понять их роли.

Если совсем грубо:

- `V8` исполняет JavaScript
- модули Node.js дают высокоуровневые API
- `libuv` помогает с асинхронной инфраструктурой и I/O
- внутренние bindings связывают всё это вместе

Когда эта схема становится понятной, многие "магические" вещи в Node.js перестают казаться магией.

Именно ради этого и полезно разбирать архитектуру в начале: не для академической красоты, а чтобы дальше осознанно понимать, почему Node.js ведёт себя именно так.

### 1. V8

`V8` это JavaScript-движок. Он выполняет ваш JS-код.

Если не вдаваться в детали, V8 можно представить как "мотор", который понимает JavaScript и умеет его запускать достаточно быстро.

Важно не путать:

- `V8` не равно `Node.js`
- `Node.js` использует `V8`

То есть V8 отвечает именно за выполнение JavaScript, но сам по себе не даёт вам, например, `fs.readFile()` или `http.createServer()`.

### 2. Встроенные модули Node.js

Например:

- `node:fs` для файловой системы
- `node:path` для путей
- `node:os` для информации об ОС
- `node:http` для HTTP-сервера
- `node:events` для событий
- `node:stream` для потоков данных

Вот это уже то, что отличает Node.js от "просто движка". Эти модули дают вам готовые инструменты для реальной работы.

### 3. libuv

`libuv` даёт Node.js кроссплатформенный неблокирующий ввод-вывод, а также связан с event loop и внутренним пулом потоков.

Проще всего думать о `libuv` как о технической части, которая помогает Node.js одинаково удобно работать на разных ОС и не подвешивать приложение на операциях ввода-вывода.

Например:

- чтение файла
- сетевые операции
- DNS-запросы
- часть криптографических операций

Часть таких задач уходит либо в возможности операционной системы, либо во внутреннюю инфраструктуру `libuv`.

### 4. C/C++ bindings

Это прослойка между JavaScript API Node.js и низкоуровневой реализацией.

### Важная мысль

Когда говорят, что Node.js однопоточный, обычно имеют в виду **выполнение JavaScript в основном потоке**.

Но при этом Node.js умеет:

- делегировать часть I/O-задач операционной системе
- использовать внутренний пул потоков `libuv` для некоторых операций
- запускать отдельные процессы
- запускать worker threads для CPU-задач

То есть формулировка "в Node.js только один поток и больше ничего нет" слишком грубая и неточная.

💡 Совет

Лучше держать в голове такую модель:

- JavaScript-код пользователя обычно исполняется в одном основном потоке
- но сам Node.js внутри устроен не настолько примитивно

Это снимает много путаницы, особенно когда начинаются разговоры про event loop, `libuv`, `worker_threads` и пул потоков.

**Кратко:**
Node.js это не только V8. Это ещё встроенные модули, `libuv` и инфраструктура, которая позволяет JavaScript-коду работать с файлами, сетью и системой.

### Типичные ошибки

- Считать, что `V8` уже сам по себе даёт все возможности Node.js.
- Считать, что `libuv` это "просто библиотека, которая где-то там есть" и не влияет на модель выполнения.
- Сводить всю архитектуру Node.js к фразе "он однопоточный", не понимая оговорок.

## Блокирующий и неблокирующий ввод-вывод

Одна из ключевых идей Node.js: не держать основной поток занятым там, где можно не держать.

Это один из самых важных моментов во всём Node.js.

Когда приложение работает с файлами, сетью, базой данных или внешним API, очень часто большая часть времени уходит не на вычисления, а на ожидание:

- пока придёт ответ по сети
- пока диск прочитает файл
- пока база вернёт данные

Если в этот момент держать основной поток занятым и просто ждать, приложение начнёт тормозить без всякой пользы.

Идея Node.js простая: если можно не стоять над задачей и не ждать её вручную, лучше поручить её системе и вернуться к ней позже.

### Синхронный вариант

```js
import { readFileSync } from 'node:fs';

const text = readFileSync('./message.txt', 'utf8');

console.log('Файл прочитан');
console.log(text);
console.log('Дальше код пойдёт только после чтения файла');
```

Здесь выполнение остановится на `readFileSync`, пока файл не будет прочитан.

### Асинхронный вариант через промисы

```js
import { readFile } from 'node:fs/promises';

async function main() {
  const text = await readFile('./message.txt', 'utf8');

  console.log('Файл прочитан');
  console.log(text);
}

main().catch((error) => {
  console.error('Ошибка чтения файла:', error.message);
});
```

### Асинхронный вариант через колбэк

```js
import { readFile } from 'node:fs';

readFile('./message.txt', 'utf8', (error, text) => {
  if (error) {
    console.error('Ошибка чтения файла:', error.message);
    return;
  }

  console.log('Файл прочитан');
  console.log(text);
});

console.log('Этот лог выполнится раньше завершения чтения');
```

### Когда синхронный код допустим

- маленькие одноразовые скрипты
- код инициализации до старта сервера
- CLI-утилиты, где простота важнее максимальной производительности

Например, если у вас маленький скрипт, который один раз читает конфиг, что-то делает и завершает работу, синхронное чтение часто вообще нормально.

Проблема начинается тогда, когда этот же подход попадает в серверный код, который должен параллельно обслуживать много пользователей.

### Когда синхронный код опасен

- внутри HTTP-обработчиков
- в приложении с множеством одновременных запросов
- при работе с большими файлами
- в местах, где важна отзывчивость приложения

Важно

Синхронные API сами по себе не "плохие". Они плохи там, где блокировка основного потока реально мешает приложению.

Мини-вывод:

Node.js любит асинхронность не потому, что это модно, а потому что это позволяет не простаивать во время ожидания I/O.

**Кратко:**
Синхронный код проще, но он блокирует поток выполнения. Асинхронный код сложнее, зато позволяет Node.js обслуживать другие задачи, пока текущая операция ждёт завершения.

### Типичные ошибки

- Использовать `readFileSync` и похожие sync API прямо внутри HTTP-обработчиков.
- Думать, что асинхронный код всегда быстрее сам по себе.
- Не различать сценарии "маленький одноразовый скрипт" и "долго живущий сервер".

## Event Loop простыми словами

Event loop это механизм, который помогает Node.js обрабатывать асинхронные события без создания отдельного потока под каждый запрос.

Это одна из центральных тем во всём Node.js. Если её понять нормально, дальше и HTTP, и стримы, и работа с файлами, и асинхронный код начинают укладываться намного легче.

Если нужна бытовая аналогия, можно представить маленький офис с одним очень организованным менеджером.

У менеджера одна голова и одна пара рук, но он не делает всё лично от начала до конца.

Он работает так:

1. Принимает задачу.
2. Если задача требует ожидания, например ответа от другого отдела, он не сидит и не смотрит в стену.
3. Он откладывает эту задачу в ожидание и берёт следующую.
4. Когда приходит сигнал, что ожидание закончено, он возвращается к задаче.

Event loop работает примерно в таком духе. Он не делает JavaScript многопоточным магически. Он просто не даёт приложению бессмысленно простаивать там, где можно продолжать работу.

Если упростить, схема такая:

1. JavaScript-код запускается.
2. Асинхронные операции регистрируются.
3. Когда операция завершается, её колбэк попадает в очередь.
4. Event loop по очереди берёт готовые задачи и передаёт их на выполнение.

### Основные фазы event loop

В упрощённом виде полезно помнить такие фазы:

- `timers`
- `pending callbacks`
- `poll`
- `check`
- `close callbacks`

Часто для понимания на старте хватает такой схемы:

`timers -> poll -> check -> close`

Но это именно упрощение. Полная картина сложнее.

Здесь полезно уловить не идеальную академическую схему, а практический смысл фаз:

- `timers` отвечает за таймеры вроде `setTimeout` и `setInterval`
- `poll` это место, где Node.js получает и обрабатывает много I/O-событий
- `check` это зона, где выполняется `setImmediate`
- `close callbacks` это обработчики закрытия ресурсов

То есть event loop не просто "крутится по кругу". Он проходит по предсказуемым этапам, и от этого зависит порядок выполнения асинхронного кода.

### `process.nextTick()` и `setImmediate()`

Это два частых источника путаницы.

#### `process.nextTick()`

```js
console.log('start');

process.nextTick(() => {
  console.log('nextTick');
});

console.log('end');
```

Результат:

```txt
start
end
nextTick
```

`process.nextTick()` выполняется **после завершения текущего стека вызовов**, но **до перехода event loop к следующим фазам**.

Из-за этого `process.nextTick()` ощущается как что-то "очень срочное". Он не уходит в обычную очередь фаз event loop так же, как таймеры или `setImmediate`.

Именно поэтому с ним нужно быть аккуратным. Если рекурсивно и без меры ставить новые `nextTick`, можно надолго не дать event loop заняться остальными задачами.

#### `setImmediate()`

```js
console.log('start');

setImmediate(() => {
  console.log('setImmediate');
});

console.log('end');
```

`setImmediate()` планирует колбэк на следующую итерацию event loop, обычно на фазу `check`.

По смыслу `setImmediate()` часто удобнее, когда вы хотите сказать:

"Сделай это не прямо сейчас, а как только закончится текущая работа цикла."

### Что важно запомнить

- `process.nextTick()` срабатывает раньше `setImmediate()`
- злоупотребление `process.nextTick()` может "задушить" event loop
- `setImmediate()` обычно проще для понимания, когда надо просто отложить выполнение

### Сравнение на одном примере

```js
console.log('1');

setTimeout(() => console.log('2: timeout'), 0);

setImmediate(() => console.log('3: immediate'));

process.nextTick(() => console.log('4: nextTick'));

Promise.resolve().then(() => console.log('5: promise'));

console.log('6');
```

Типичный порядок:

```txt
1
6
4: nextTick
5: promise
2: timeout
3: immediate
```

Но порядок `setTimeout(..., 0)` и `setImmediate()` в общем случае не стоит считать абсолютно гарантированным вне конкретного контекста. Например, внутри I/O-колбэка поведение будет другим.

Это важный момент, потому что очень многие пытаются запомнить один "магический" универсальный порядок и потом удивляются, почему на практике видят другое поведение.

Здесь лучше помнить не жёсткий список, а принцип:

- `nextTick` приоритетнее
- колбэки промисов тоже очень ранние
- `setTimeout(..., 0)` это не "мгновенно"
- `setImmediate()` живёт в своей фазе

Важно

Фраза "все функции в Node.js выполняются асинхронно" неверна. Обычный JavaScript-код выполняется синхронно. Асинхронность появляется там, где вы используете соответствующие API.

Ещё одна полезная мысль: event loop не делает долгий код быстрым. Он помогает разумно чередовать готовые задачи и не блокироваться там, где можно этого избежать.

**Кратко:**
Event loop это сердце асинхронной модели Node.js. `process.nextTick()` выполняется раньше, `setImmediate()` позже, а путать их с обычным синхронным кодом не стоит.

### Типичные ошибки

- Пытаться запомнить порядок всех очередей как магическую формулу без понимания контекста.
- Злоупотреблять `process.nextTick()` и случайно душить event loop.
- Думать, что `setTimeout(fn, 0)` означает "выполнить прямо сейчас".

## Как можно случайно заблокировать event loop

Самая частая проблема не в файлах и не в сети, а в том, что разработчик сам долго держит поток занятым.

Это очень частая ошибка у новичков. Кажется, что если код "просто считает", то ничего страшного не происходит. Но для Node.js длинные вычисления в основном потоке часто опаснее, чем ожидающий сетевой запрос.

Почему:

- пока крутится тяжёлый цикл, event loop не может нормально перейти к другим задачам
- новые HTTP-запросы ждут
- таймеры ждут
- события стримов ждут
- приложение начинает казаться "подвисшим"

### Плохой пример

```js
let total = 0;

for (let i = 0; i < 2_000_000_000; i += 1) {
  total += i;
}

console.log(total);
```

Пока цикл крутится, Node.js не сможет нормально обрабатывать другие события.

### Более аккуратный подход

```js
function delayImmediate() {
  return new Promise((resolve) => {
    setImmediate(resolve);
  });
}

async function processItems(items) {
  let total = 0;

  for (let i = 0; i < items.length; i += 1) {
    total += items[i];

    // Периодически отдаём управление event loop.
    if (i % 10_000 === 0) {
      await delayImmediate();
    }
  }

  return total;
}
```

Это не делает тяжёлую задачу бесплатной, но позволяет не замораживать приложение полностью.

### Что делать для CPU-heavy задач

- использовать `worker_threads`
- выносить тяжёлую обработку в отдельный сервис
- ставить задачи в очередь
- не выполнять долгие вычисления прямо в HTTP-обработчике

Мини-вывод:

Если задача "долго думает", а не "долго ждёт", это уже не типичная I/O-задача. И подход к ней нужен другой.

**Кратко:**
Event loop чаще всего блокируют не встроенные модули, а тяжёлые циклы и вычисления в основном потоке. Если задача CPU-тяжёлая, её лучше вынести из main thread.

### Типичные ошибки

- Запускать тяжёлые вычисления прямо внутри обработчика запроса.
- Считать, что если код "без файлов и без сети", то он не мешает event loop.
- Пытаться лечить CPU-проблему таймерами вместо выноса задачи в `worker_threads` или отдельный сервис.

## npm: что это и как с ним работать

`npm` это менеджер пакетов, который ставится вместе с Node.js.

На практике знакомство с Node.js почти всегда быстро упирается в `npm`, потому что современный проект почти никогда не живёт совсем без зависимостей, скриптов и `package.json`.

Важно уточнить: сейчас `npm` обычно рассматривают как название инструмента, а не как официальную расшифровку "Node Package Manager".

### Инициализация проекта

```bash
npm init
```

Или без вопросов:

```bash
npm init -y
```

После этого появится `package.json`.

### Что обычно лежит в `package.json`

- имя проекта
- версия
- описание
- скрипты
- зависимости
- devDependencies

По сути `package.json` это паспорт проекта.

В нём описывается:

- как проект называется
- какие пакеты ему нужны
- какие команды можно запускать
- какой формат модулей используется
- какие есть метаданные

Когда проект становится больше одного файла, `package.json` почти всегда становится центром всей конфигурации.

Можно сказать, что если `index.js` или `server.js` это точка входа в код, то `package.json` это точка входа в проект как в рабочую единицу.

### Установка пакета

```bash
npm install express
```

Для зависимостей разработки:

```bash
npm install -D nodemon
```

### Удаление пакета

```bash
npm uninstall express
```

### Скрипты

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node index.js",
    "dev": "node --watch index.js"
  }
}
```

Запуск:

```bash
npm run dev
```

Или, если это `start`, можно короче:

```bash
npm start
```

Скрипты удобны тем, что прячут длинные команды.

Например, вместо того чтобы каждый раз помнить:

```bash
node --watch --env-file=.env index.js
```

можно описать это в `package.json` и запускать коротко:

```bash
npm run dev
```

Это особенно полезно в командах, чтобы у всех были одинаковые команды запуска.

### Что важно понимать про `node_modules`

`node_modules` часто огромная папка, потому что пакеты тянут зависимости рекурсивно.

Поэтому обычно:

- `node_modules` не коммитят в git
- коммитят `package.json`
- коммитят lock-файл: `package-lock.json`

Lock-файл важен, потому что он фиксирует точные версии пакетов и подзависимостей.

Без него возможно такое:

- у вас проект работает
- коллега делает `npm install`
- ему прилетает чуть другая версия зависимостей
- поведение уже отличается

С `package-lock.json` среда получается куда более предсказуемой.

💡 Совет

Если проект скачан из репозитория, обычно достаточно выполнить:

```bash
npm install
```

чтобы восстановить зависимости.

Кроме установки пакетов, `npm` на практике становится ещё и единым входом в команды проекта. Через него запускают:

- dev-режим
- тесты
- линтеры
- сборку
- миграции
- сиды

То есть `npm` это не только "скачать пакет", но и удобный центр командной работы над проектом.

**Кратко:**
`npm` управляет зависимостями и скриптами проекта. Минимальная база: `npm init -y`, `npm install`, `npm uninstall`, `npm run <script>`.

### Типичные ошибки

- Коммитить `node_modules` в репозиторий.
- Игнорировать `package-lock.json`.
- Ставить всё подряд в `dependencies`, даже если пакет нужен только для разработки.
- Думать, что `npm` нужен только для внешних библиотек, а скрипты лучше запускать руками.

## Модули в Node.js

Каждый файл в Node.js это отдельный модуль.

Это очень важная идея, потому что она дисциплинирует структуру проекта.

Вместо того чтобы держать всё в одном огромном файле, вы разбиваете код на части:

- работа с пользователями
- работа с файлами
- конфиг
- роуты
- утилиты

А потом явно импортируете только то, что нужно.

Это важно не только для красоты. Модули делают код:

- понятнее
- переиспользуемее
- проще для тестирования
- проще для поддержки

На практике вам важно знать два формата:

- `CommonJS`
- `ES Modules`

### CommonJS

Импорт:

```js
const fs = require('node:fs');
```

Экспорт:

```js
function sum(a, b) {
  return a + b;
}

module.exports = { sum };
```

Импорт этого модуля:

```js
const { sum } = require('./math');

console.log(sum(2, 3));
```

`CommonJS` это исторический формат модулей Node.js. Его важно понимать, потому что:

- он до сих пор часто встречается в старых проектах
- многие пакеты долгое время публиковались именно так
- в вопросах собеседований и legacy-коде он встречается постоянно

### ES Modules

Экспорт:

```js
export function sum(a, b) {
  return a + b;
}
```

Импорт:

```js
import { sum } from './math.js';

console.log(sum(2, 3));
```

`ES Modules` это уже стандартный современный синтаксис JavaScript.

Если проект новый, чаще всего имеет смысл писать именно на нём, особенно если он и в браузере, и на сервере использует единый подход.

На практике выбор формата модулей влияет не только на синтаксис, но и на мелкие рабочие вещи:

- как вы импортируете файлы
- нужен ли `"type": "module"` в `package.json`
- как ведут себя старые пакеты
- какие примеры из интернета подойдут без изменений, а какие нет

Поэтому важно не просто знать два синтаксиса, а понимать, что это два реально разных режима работы модульной системы.

### Важный подводный камень с `exports`

Вот так можно:

```js
exports.sum = (a, b) => a + b;
```

Но вот так делать опасно:

```js
exports = (a, b) => a + b;
```

Почему? Потому что `exports` это только короткая ссылка на `module.exports`. Если переприсвоить сам `exports`, связь потеряется.

Правильно для единственного экспорта:

```js
module.exports = (a, b) => a + b;
```

### Ещё одна частая ошибка

Неправильно:

```js
module.export = ['Nick', 'Daniel'];
```

Правильно:

```js
module.exports = ['Nick', 'Daniel'];
```

Важно

Если смешивать `CommonJS` и `ESM` без понимания контекста, можно словить очень неприятные ошибки импорта. В одном проекте лучше сразу договориться, какой модульный формат вы используете.

💡 Совет

Для учебного проекта можно выбрать один из вариантов и держаться его до конца конспекта. Так в голове будет меньше путаницы.

### Как Node.js ищет модули

Когда вы пишете:

```js
import fs from 'node:fs';
```

или:

```js
const fs = require('node:fs');
```

Node.js понимает, что это встроенный модуль.

Когда вы пишете:

```js
import express from 'express';
```

Node.js ищет пакет в `node_modules`.

А когда вы пишете:

```js
import { sum } from './math.js';
```

Node.js понимает, что это локальный файл относительно текущего модуля.

Это кажется очевидным, но на практике очень часто именно здесь возникают ошибки:

- забыли `./`
- забыли расширение
- ожидали, что пакет встроенный, а он внешний
- перепутали абсолютный и относительный путь

Поэтому в модульной системе Node.js мелочи реально важны. Одна забытая точка или расширение может полностью сломать импорт.

**Кратко:**
В Node.js каждый файл это модуль. Для `CommonJS` используются `require()` и `module.exports`, для `ESM` используются `import` и `export`.

### Типичные ошибки

- Смешивать `CommonJS` и `ESM`, не понимая, какой формат у текущего проекта.
- Писать `module.export` вместо `module.exports`.
- Переприсваивать `exports` и ожидать, что экспорт продолжит работать.
- Забывать расширение `.js` в ESM-импортах там, где оно нужно.

## Встроенные модули, которые нужно знать в первую очередь

### `process`

Объект `process` даёт доступ к информации о текущем процессе.

```js
console.log('PID:', process.pid);
console.log('Платформа:', process.platform);
console.log('Аргументы:', process.argv);
console.log('Переменная окружения NODE_ENV:', process.env.NODE_ENV);
```

`process` часто используют для:

- чтения переменных окружения
- завершения процесса
- получения аргументов командной строки
- диагностики среды запуска

### `path`

Помогает безопасно собирать пути.

```js
import path from 'node:path';

const filePath = path.join(process.cwd(), 'files', 'data.txt');

console.log(filePath);
```

`path` особенно важен на Windows и Linux/macOS, потому что разделители путей отличаются. Руками склеивать пути строками плохая идея.

### `os`

Информация об операционной системе:

```js
import os from 'node:os';

console.log('Платформа:', os.platform());
console.log('CPU:', os.cpus().length);
console.log('Домашняя папка:', os.homedir());
```

### `fs`

Работа с файлами:

```js
import { writeFile, readFile } from 'node:fs/promises';

async function main() {
  await writeFile('./note.txt', 'Привет из Node.js');

  const content = await readFile('./note.txt', 'utf8');
  console.log(content);
}

main().catch((error) => {
  console.error('Ошибка:', error.message);
});
```

На практике `fs` используют очень часто:

- чтение конфигов
- запись логов
- работа с шаблонами
- загрузка и сохранение файлов
- обработка директорий

Здесь важно понимать ещё одну вещь: у `fs` есть несколько стилей API.

- синхронный
- колбэк-ориентированный
- промисный
- стримовый

Это не четыре разные темы, а просто четыре способа решать разные задачи одним семейством инструментов.

Условно:

- быстрое чтение маленького файла в скрипте: sync или promises
- серверная логика: чаще promises
- потоковая передача большого файла: streams
- старый код или callback-style API: колбэки

**Кратко:**
Минимальный набор встроенных модулей, которые реально нужны почти сразу: `process`, `path`, `os`, `fs`.

### Типичные ошибки

- Склеивать пути вручную строками вместо `path.join()` или `path.resolve()`.
- Читать переменные окружения где попало и без проверки на наличие.
- Использовать `fs` без обработки ошибок.
- Писать код так, будто все пути и поведение файловой системы одинаковы на всех ОС.

## EventEmitter и событийная модель

Многие API Node.js построены вокруг событий.

Смысл событийной модели очень простой:

- есть событие
- есть подписчики
- когда событие происходит, подписчики реагируют

Это удобно, когда один кусок кода не должен жёстко зависеть от другого. Вместо прямого вызова можно просто "сгенерировать событие".

### Базовый пример

```js
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();

emitter.on('message', (text) => {
  console.log('Получено сообщение:', text);
});

emitter.emit('message', 'Привет');
```

### Событие только один раз

```js
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();

emitter.once('ready', () => {
  console.log('Событие ready сработает только один раз');
});

emitter.emit('ready');
emitter.emit('ready');
```

### Подводный камень

Слушатели `EventEmitter` вызываются синхронно в момент `emit()`.

Если обработчик тяжёлый, он тоже может тормозить поток.

Это важный нюанс. Иногда кажется, что раз речь идёт про "события", значит всё там автоматически асинхронно. Нет. Сам по себе `emit()` вызывает слушатели синхронно.

Если нужна асинхронность, её нужно организовать отдельно.

**Кратко:**
`EventEmitter` это базовый механизм подписки и генерации событий. Он часто встречается внутри Node.js API и полезен для собственной архитектуры.

### Типичные ошибки

- Считать, что `emit()` автоматически делает код асинхронным.
- Не удалять лишние подписки там, где объект живёт долго.
- Использовать события там, где проще и понятнее обычный вызов функции.

## Стримы

Стримы нужны, когда данные лучше обрабатывать частями, а не грузить целиком в память.

Это тема, которую сначала многие недооценивают, а потом понимают, что без неё сложно писать нормальный серверный код.

Если файл маленький, его можно просто целиком прочитать в память.

Но если файл большой, это уже плохая идея:

- растёт потребление памяти
- выше риск тормозов
- дольше первый отклик
- хуже масштабируемость

Стрим решает это тем, что отдаёт данные кусками.

### Основные типы стримов

- `Readable` можно читать
- `Writable` можно писать
- `Duplex` можно и читать, и писать
- `Transform` можно читать, писать и преобразовывать данные

### Чтение файла потоком

```js
import { createReadStream } from 'node:fs';

const stream = createReadStream('./big-file.txt', {
  encoding: 'utf8',
});

stream.on('data', (chunk) => {
  console.log('Новый кусок данных:', chunk.length);
});

stream.on('end', () => {
  console.log('Чтение завершено');
});

stream.on('error', (error) => {
  console.error('Ошибка стрима:', error.message);
});
```

### Запись в файл

```js
import { createWriteStream } from 'node:fs';

const stream = createWriteStream('./output.txt', {
  encoding: 'utf8',
});

stream.write('Первая строка\n');
stream.write('Вторая строка\n');
stream.end('Финальная строка\n');
```

### `pipe()` и передача данных без ручной сборки

Очень частый и удобный паттерн со стримами:

```js
import { createReadStream, createWriteStream } from 'node:fs';

const source = createReadStream('./input.txt');
const target = createWriteStream('./copy.txt');

source.pipe(target);
```

В таком виде Node.js сам связывает читаемый поток с записываемым и по мере готовности передаёт данные дальше.

Это особенно полезно, когда не хочется вручную собирать чанки через `data`.

### Почему стримы важны

- меньше расход памяти
- удобно передавать большие файлы
- естественно подходят для HTTP
- хорошо работают в пайплайнах

Аналогия простая:

- `readFile` это как принести весь грузовик товара сразу на склад
- стрим это как подавать коробки по одной на ленту

Если товара очень много, второй вариант намного удобнее.

Важно

Не смешивайте несколько способов чтения одного и того же `Readable` без необходимости. Например, `on('data')` и `pipe()` вместе часто приводят к странному поведению.

Ещё один практический момент: стримы почти всегда требуют внимания к ошибкам и завершению потока. Если об этом забыть, приложение может работать нестабильно и давать трудноуловимые баги.

Если говорить совсем просто, стримы это не "сложная низкоуровневая экзотика", а нормальный рабочий способ сказать:

"Не держи всё в памяти сразу. Передавай по кускам."

**Кратко:**
Стримы позволяют работать с данными по кускам. Это особенно полезно для больших файлов, HTTP и любых сценариев, где не хочется тащить всё в память сразу.

### Типичные ошибки

- Читать огромные файлы целиком, хотя логичнее использовать стрим.
- Забывать подписку на `'error'`.
- Пытаться одновременно управлять стримом через `pipe()` и вручную через `data`.
- Не думать о backpressure, когда поток записи не успевает принимать данные.

## HTTP-сервер на чистом Node.js

Node.js позволяет поднимать HTTP-сервер без Express и других фреймворков.

Это полезно изучить хотя бы один раз, даже если дальше вы будете писать на Express, Fastify или Nest.

Почему это важно:

- становится понятно, что реально происходит под капотом
- исчезает магия вокруг `req`, `res`, роутов и тела запроса
- проще отлаживать серверное поведение

Когда этот слой становится понятным, фреймворки перестают выглядеть как магия. Вы начинаете видеть в них не "чёрный ящик", а просто более удобную обёртку над знакомыми концепциями.

### Простейший сервер

```js
import http from 'node:http';

const server = http.createServer((req, res) => {
  res.statusCode = 200;
  res.setHeader('Content-Type', 'text/plain; charset=utf-8');
  res.end('Сервер работает');
});

server.listen(3000, () => {
  console.log('Server started on http://localhost:3000');
});
```

### Простейшая маршрутизация

```js
import http from 'node:http';

const server = http.createServer((req, res) => {
  if (req.method === 'GET' && req.url === '/users') {
    res.setHeader('Content-Type', 'application/json; charset=utf-8');
    res.end(JSON.stringify([{ id: 1, name: 'Nick' }]));
    return;
  }

  if (req.method === 'GET' && req.url === '/') {
    res.end('Главная страница');
    return;
  }

  res.statusCode = 404;
  res.end('Route not found');
});

server.listen(3000);
```

Такой подход через `if` быстро становится неудобным, когда маршрутов много. Но для понимания основ он идеален, потому что показывает механику без абстракций.

### Чтение тела POST-запроса

```js
import http from 'node:http';

const server = http.createServer((req, res) => {
  if (req.method === 'POST' && req.url === '/users') {
    let body = '';

    req.setEncoding('utf8');

    req.on('data', (chunk) => {
      body += chunk;
    });

    req.on('end', () => {
      try {
        const user = JSON.parse(body);

        res.statusCode = 201;
        res.setHeader('Content-Type', 'application/json; charset=utf-8');
        res.end(JSON.stringify({ created: true, user }));
      } catch {
        res.statusCode = 400;
        res.end('Invalid JSON');
      }
    });

    return;
  }

  res.statusCode = 404;
  res.end('Not found');
});

server.listen(3000);
```

### Query-параметры и URL

Когда запрос становится сложнее, одного `req.url === '/users'` уже мало. Например, запрос может прийти как:

`/users?page=2&limit=10`

Тогда полезно разбирать URL явно:

```js
import http from 'node:http';

const server = http.createServer((req, res) => {
  const url = new URL(req.url, 'http://localhost:3000');

  if (req.method === 'GET' && url.pathname === '/users') {
    const page = url.searchParams.get('page') ?? '1';
    const limit = url.searchParams.get('limit') ?? '10';

    res.setHeader('Content-Type', 'application/json; charset=utf-8');
    res.end(JSON.stringify({ page, limit }));
    return;
  }

  res.statusCode = 404;
  res.end('Not found');
});

server.listen(3000);
```

Такой подход намного надёжнее, чем вручную разбирать строку запроса.

### Что важно понять про `req` и `res`

Если упростить:

- `req` описывает входящий запрос
- `res` управляет исходящим ответом

Но практически полезнее думать так:

- `req` содержит метод, URL, заголовки и поток тела запроса
- `res` содержит статус, заголовки и поток ответа

То есть HTTP в Node.js это не какая-то магия. Это довольно прозрачная работа с двумя объектами и потоками данных между клиентом и сервером.

### На что здесь обратить внимание

- `req` это читаемый стрим
- `res` это записываемый стрим
- ответ обязательно нужно завершать через `res.end()`
- тело запроса приходит частями
- JSON нужно парсить с обработкой ошибок

Очень важный момент: `req.url` и `req.method` сами по себе уже дают достаточно информации, чтобы построить самый базовый роутинг.

Именно на этом уровне потом и строятся более удобные обёртки во фреймворках.

Мини-вывод:

Express не придумывает HTTP заново. Он просто делает работу с ним удобнее.

**Кратко:**
Даже без Express можно собрать рабочий HTTP-сервер. Это полезно, чтобы понять базовую механику: маршруты, методы, тело запроса и ответ клиенту.

### Типичные ошибки

- Забывать вызвать `res.end()`.
- Пытаться читать тело запроса как будто оно приходит одной строкой.
- Не выставлять корректный `Content-Type`.
- Не обрабатывать невалидный JSON и падать на `JSON.parse`.

## Процессы, кластер и worker threads

### Процессы

Один экземпляр Node.js это отдельный процесс.

### `cluster`

Модуль `cluster` позволяет запускать несколько процессов Node.js и распределять нагрузку между ними. Исторически это был популярный способ утилизировать несколько ядер CPU для сетевых приложений.

Но сегодня важно понимать нюанс:

- `cluster` всё ещё существует
- для CPU-задач чаще смотрят в сторону `worker_threads`
- для масштабирования в проде часто используют процесс-менеджеры, контейнеры и внешние балансировщики

То есть `cluster` полезно знать, но сегодня его не стоит воспринимать как универсальное решение на все случаи.

Если говорить совсем практично:

- `cluster` помогает распараллелить несколько процессов приложения
- `worker_threads` помогает распараллелить вычисления внутри логики

Они решают похожую по ощущениям, но не одинаковую задачу.

### `worker_threads`

Если задача именно вычислительная, то `worker_threads` подходит лучше.

```js
import { Worker } from 'node:worker_threads';

const worker = new Worker(
  `
    const { parentPort } = require('node:worker_threads');
    let total = 0;

    for (let i = 0; i < 10_000_000; i += 1) {
      total += i;
    }

    parentPort.postMessage(total);
  `,
  { eval: true }
);

worker.on('message', (result) => {
  console.log('Результат из worker:', result);
});

worker.on('error', (error) => {
  console.error('Ошибка worker:', error);
});
```

Важно

`worker_threads` полезны для CPU-intensive задач. Для обычного I/O они обычно не дают выигрыша, потому что встроенные асинхронные механизмы Node.js и так работают эффективно.

Здесь важно уловить разницу:

- если задача в основном **ждёт**, worker обычно не нужен
- если задача в основном **считает**, worker может быть очень полезен

Это одно из самых практичных различий в Node.js архитектуре.

Если держать в голове только эту пару:

- I/O-задачи обычно решаются асинхронностью
- CPU-задачи часто требуют выноса вычислений

то очень много архитектурных решений уже становится проще принимать.

**Кратко:**
JavaScript в Node.js обычно выполняется в основном потоке. Для процессов есть `cluster`, а для тяжёлых вычислений сегодня чаще нужен `worker_threads`.

### Типичные ошибки

- Пытаться лечить CPU-нагрузку обычной асинхронностью без выноса вычислений.
- Использовать `worker_threads` для типичного I/O, где они не нужны.
- Считать `cluster` универсальным и современным ответом вообще на любую задачу масштабирования.

## Что особенно важно унести с собой

Если убрать детали, большая часть реальных проблем в Node.js обычно сводится к нескольким вещам:

- не поняли, где код синхронный, а где асинхронный
- заблокировали event loop тяжёлой работой
- выбрали не тот способ работы с файлами или сетью
- запутались в модулях и формате импорта
- забыли, что HTTP и стримы часто работают кусками, а не цельным значением

Это и есть та база, на которой потом уже строятся Express, Fastify, Nest, очереди, WebSocket-серверы, работа с базами и всё остальное.

**Кратко:**
Если вы уверенно понимаете event loop, модули, `npm`, I/O, стримы и базовый HTTP, то фундамент Node.js уже собран правильно.

После этого конспекта логично двигаться в таком порядке:

1. Научиться уверенно писать небольшие CLI-скрипты и утилиты на Node.js.

## Итог

Node.js хорош тогда, когда вы понимаете его модель:

- JavaScript выполняется в основном потоке
- I/O лучше делать асинхронно
- event loop нужно беречь
- модули и зависимости нужно держать в порядке
- стримы и события это не экзотика, а база
- для тяжёлых вычислений нужны отдельные механизмы

Если уложить это в голове, Node.js перестаёт быть "чёрным ящиком" и становится вполне понятным рабочим инструментом.

**Кратко:**
Главная идея Node.js не в том, что он "магически быстрый", а в том, что он очень эффективно работает с большим количеством I/O-задач, если не мешать ему блокирующим кодом.
