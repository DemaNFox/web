# Code Style, Workflow и внедрение порядка в JavaScript-проекте

Когда работаешь один, можно довольно долго жить без жестких правил. Ты и так примерно понимаешь, что написал вчера, зачем это написал и почему вот тут стоит именно такой код.

Но как только в проект приходит второй человек, магия заканчивается. Потом приходит третий. Потом кто-то приносит свой любимый стиль. Потом кто-то еще пишет коммиты по-русски, кто-то по-английски, кто-то именует ветки как попало, а кто-то форматирует код просто по зову сердца.

И вот в этот момент становится понятно: без правил команда начинает тратить время не на продукт, а на расшифровку того, что хотел сказать автор.

Этот материал про то, как навести порядок без фанатизма:

- выбрать нормальный code style;
- автоматизировать проверки;
- не превращать code review в спор про пробелы;
- встроить все это в Git и CI;
- при необходимости писать свои правила и даже код-моды.

> **Важно**
> Главная идея простая: не надо изобретать свой великий уникальный стиль, если можно взять готовый, понятный и поддерживаемый сообществом.

## Кратко:

- Code style нужен не ради красоты, а ради скорости и предсказуемости.
- Чем больше команда, тем дороже отсутствие правил.
- Лучший стиль обычно не "самый умный", а тот, который уже кто-то поддерживает вместо вас.

## Зачем вообще нужен code style

Если коротко, code style нужен не для того, чтобы спорить, где ставить пробел.

Он нужен для трех вполне практичных вещей:

1. Чтобы код было легче читать.
2. Чтобы новые люди быстрее входили в проект.
3. Чтобы команда тратила меньше времени на ерунду.

Когда код везде выглядит примерно одинаково, мозг перестает тратить силы на форму и начинает смотреть на смысл. Это как если в городе все дорожные знаки были бы нарисованы в разном стиле. Доехать можно, но зачем так мучиться.

### Что именно стоит стандартизировать

Обычно речь не только про форматирование.

Нужно договориться хотя бы про это:

- стиль JavaScript-кода;
- стиль CSS / SCSS / PostCSS;
- формат коммитов;
- именование веток;
- правила code review;
- локальный workflow;
- проверки перед merge;
- базовые требования к документации и тестам.

### Где реально появляется выигрыш

Выигрыш чаще всего вот здесь:

- уменьшается шум в pull request;
- новые разработчики быстрее понимают проект;
- проще искать ошибки;
- легче делать массовые изменения;
- меньше споров "а я привык вот так".

### Мини-пример

Без единого стиля один и тот же код может выглядеть вот так:

```js
function getUserData(id){
return fetch('/api/users/'+id).then((r)=>r.json())
}
```

А после нормализации так:

```js
function getUserData(id) {
  return fetch(`/api/users/${id}`).then((response) => response.json());
}
```

Во втором варианте нет откровений, зато его не больно читать.

## Кратко:

- Code style снижает когнитивную нагрузку.
- Стандартизировать стоит не только код, но и рабочий процесс.
- Самый заметный эффект обычно виден в code review и онбординге.

## Как выбирать style guide

Основной принцип выбора очень простой: пусть его поддерживает кто-то другой.

Если вы придумали свой авторский стандарт, значит:

- вам надо его документировать;
- вам надо его обновлять;
- вам надо объяснять его каждому новичку;
- вам надо самим разруливать все спорные случаи.

Обычно это плохая сделка.

### Что брать на практике

Нормальный путь выглядит так:

- взять готовый популярный стиль;
- добавить минимум project-specific правил;
- не трогать то, без чего можно жить.

Для JavaScript-проектов долгое время часто брали Airbnb. Это не единственный вариант, но логика выбора там здравая: стиль известный, документация есть, люди его уже видели.

Сейчас на практике многие команды идут одним из двух путей:

1. `ESLint + @eslint/js + свои точечные правила + Prettier`
2. `ESLint + готовый shareable config + Prettier`

### Чего лучше не делать

- Не плодить десятки кастомных правил без веской причины.
- Не воевать за вкусовщину.
- Не тащить правило в проект только потому, что "красиво".

> **💡 Совет**
> Если правило не ловит баги, не ускоряет чтение кода и не уменьшает хаос, подумай, а нужно ли оно вообще.

### Пример базовой конфигурации ESLint

```js
// eslint.config.js
import { defineConfig } from "eslint/config";
import js from "@eslint/js";
import globals from "globals";

export default defineConfig([
  {
    files: ["**/*.js"],
    plugins: {
      js,
    },
    extends: ["js/recommended"],
    languageOptions: {
      ecmaVersion: "latest",
      sourceType: "module",
      globals: {
        ...globals.browser,
        ...globals.node,
      },
    },
    rules: {
      // Не даем случайно оставлять неиспользуемые переменные
      "no-unused-vars": ["error", { argsIgnorePattern: "^_" }],

      // Лучше строгие сравнения, чтобы не ловить сюрпризы с приведением типов
      eqeqeq: ["error", "always"],

      // Для консольного кода можно смягчить правило, для прод-кода обычно оставляют warn/error
      "no-console": "warn",
    },
  },
]);
```

Если проект не использует ESM в конфиге, то официальный путь для `eslint.config.js` в CommonJS-режиме будет другим: через `require()` и `module.exports`.

### Edge-case: "у нас legacy, нам не подойдет строгий конфиг"

Подойдет, если внедрять поэтапно.

Необязательно чинить весь проект за один день. Можно:

- сначала запускать линтер только на новых файлах;
- потом только на измененных;
- потом постепенно ужесточать правила;
- старые нарушения оставлять как техдолг с понятным планом.

## Кратко:

- Лучший style guide обычно готовый, а не самодельный.
- Кастомных правил должно быть мало.
- Legacy не повод отказаться от правил, это повод внедрять их постепенно.

## С чего начать: EditorConfig, ESLint, Stylelint, Prettier

Если хочется быстро навести порядок, начинать лучше не с великой архитектуры, а с базы.

### 1. EditorConfig

`EditorConfig` решает самые скучные, но очень надоедливые вещи:

- отступы;
- кодировку;
- перевод строки;
- финальную пустую строку;
- пробелы в конце строк.

Пример:

```ini
# .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
indent_style = space
indent_size = 2
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false
```

Это не линтер и не форматтер. Он просто заставляет редакторы не вредить.

### 2. ESLint

`ESLint` проверяет JavaScript и TypeScript-код на ошибки, спорные места и нарушение правил.

Пример команды:

```json
{
  "scripts": {
    "lint:js": "eslint ."
  }
}
```

Если нужна автоматическая правка безопасных вещей:

```json
{
  "scripts": {
    "lint:js": "eslint .",
    "lint:js:fix": "eslint . --fix"
  }
}
```

### 3. Stylelint

Для CSS нужен отдельный линтер. JavaScript-линтером тут не отделаться.

```json
{
  "scripts": {
    "lint:css": "stylelint \"**/*.css\"",
    "lint:css:fix": "stylelint \"**/*.css\" --fix"
  }
}
```

Для `SCSS`, `Less`, `PostCSS` и других CSS-подобных форматов уже нужна соответствующая конфигурация, например community config или `customSyntax`.

### 4. Prettier

`Prettier` не спорит, а просто форматирует код. В этом и сила.

Он особенно хорош там, где люди начинают слишком много думать про переносы, кавычки и ширину строк.

```json
{
  "scripts": {
    "format": "prettier . --write",
    "format:check": "prettier . --check"
  }
}
```

Пример конфигурации:

```json
{
  "semi": true,
  "singleQuote": false,
  "trailingComma": "all",
  "printWidth": 100
}
```

### Важно: ESLint и Prettier не одно и то же

Это частая путаница.

- `ESLint` ищет проблемы и нарушения правил.
- `Prettier` форматирует код.

Их обычно используют вместе.

### Мини-пример с современным JavaScript

```js
// До форматирования и линтинга
const loadUser=async(id)=>{
  if(id==null){return null}
  const response = await fetch(`/api/users/${id}`)
  return response.json()
}
```

```js
// После линтинга и форматирования
const loadUser = async (id) => {
  if (id == null) {
    return null;
  }

  const response = await fetch(`/api/users/${id}`);
  return response.json();
};
```

> **Важно**
> `--fix` не чинит все на свете. Он исправляет только то, что можно безопасно исправить автоматически.

## Кратко:

- `EditorConfig` выравнивает поведение редакторов.
- `ESLint` следит за JavaScript.
- `Stylelint` следит за стилями.
- `Prettier` убирает споры про форматирование.

## Как встроить проверки в редактор

Если разработчик видит ошибку только на CI, это уже поздновато.

Идея простая: редактор должен ругаться сразу, пока код еще теплый.

### Что обычно включают

- ESLint plugin;
- Stylelint plugin;
- Prettier plugin;
- автоформатирование при сохранении.

Конкретные ключи в настройках редактора зависят от версии редактора и расширений, поэтому здесь безопаснее держаться официальных инструкций для вашей IDE, а не копировать старый JSON из статьи или чьего-то скриншота.

### Подводный камень

Если одновременно включить несколько форматтеров без понимания, кто главный, они начнут драться.

Классический симптом:

- сохраняешь файл;
- форматирование прыгает туда-сюда;
- виноваты обычно конфликтующие расширения.

Решение:

- выбрать один источник правды для форматирования;
- проверить настройки `formatOnSave`;
- убедиться, что ESLint и Prettier не делают одно и то же в конфликтующих местах.

## Кратко:

- Чем раньше видишь ошибку, тем дешевле ее исправить.
- Проверки в редакторе экономят время всей команде.
- Один форматтер должен быть главным, иначе начнется цирк.

## Git hooks: как не пускать мусор в репозиторий

Люди ленивые. Это не оскорбление, это просто важный факт проектирования процессов.

Если запуск линтера оставить "на совесть", часть команды будет забывать, откладывать или надеяться на авось.

Поэтому нужны автоматические проверки перед коммитом.

### Почему не стоит полагаться на голые git hooks вручную

Потому что:

- их неудобно раздавать команде;
- они не живут нормально внутри репозитория без дополнительной обвязки;
- на разных ОС начинаются свои приключения.

На практике обычно берут `Husky` и `lint-staged`.

### Husky + lint-staged

`Husky` подключает git hooks к проекту.

`lint-staged` запускает проверки только на измененных файлах. Это важно, иначе на большом проекте можно состариться, пока линтер проверит все.

Пример:

```json
{
  "scripts": {
    "lint:js": "eslint .",
    "lint:css": "stylelint \"src/**/*.{css,scss}\"",
    "format": "prettier . --write"
  },
  "lint-staged": {
    "*.{js,mjs,cjs,jsx,ts,tsx}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{css,scss,md,json}": [
      "prettier --write"
    ]
  }
}
```

Пример pre-commit hook:

```sh
npx lint-staged
```

### Важно про `--no-verify`

Да, любой локальный hook можно обойти через `git commit --no-verify`.

Поэтому hooks важны, но они не последняя линия обороны.

Последняя линия обороны должна быть на сервере:

- branch protection;
- обязательный CI;
- запрет merge при упавших проверках.

## Кратко:

- Локальные проверки полезны, потому что срабатывают быстро.
- `lint-staged` сильно ускоряет pre-commit.
- На одних только hooks нельзя полагаться, их можно обойти.

## CI и защита веток

Если локальные правила можно обойти, значит нужен контроль на стороне репозитория.

Нормальная схема обычно такая:

1. В protected ветки нельзя пушить напрямую.
2. Попасть туда можно только через merge request / pull request.
3. Перед merge обязателен успешный pipeline.
4. По возможности нужен code review.

### Пример GitLab CI

```yaml
# .gitlab-ci.yml
image: node:20

stages:
  - test

cache:
  paths:
    - node_modules/

lint:
  stage: test
  script:
    - npm ci
    - npm run lint:js
    - npm run lint:css
    - npm run format:check
```

### Что это дает

- нельзя случайно затащить плохой код в основную ветку;
- нельзя "забыть" прогнать проверки;
- команда спорит меньше, потому что часть решений уже формализована.

### Edge-case: pipeline слишком долгий

Если проверки идут вечность, люди начнут их ненавидеть и искать обходы.

Тут помогает:

- разделение быстрых и медленных джоб;
- кэширование зависимостей;
- проверка только нужных шагов;
- вынесение тяжелых тестов в отдельные стадии.

> **💡 Совет**
> Самые быстрые проверки лучше запускать первыми. Пусть pipeline падает быстро, а не через 15 минут.

## Кратко:

- Локальные проверки нужны для удобства.
- Серверные проверки нужны для надежности.
- Protected branches и обязательный CI резко уменьшают шанс завезти мусор в main.

## Формат коммитов и именование веток

Workflow тоже должен быть договорен заранее. Иначе потом начинается археология.

### Что стоит стандартизировать

- формат названия ветки;
- формат commit message;
- правила merge;
- кто и когда делает review.

Пример именования веток:

```txt
feature/PLATFORM-142-add-user-cache
fix/PLATFORM-201-handle-empty-response
chore/PLATFORM-333-update-eslint-config
```

Пример commit message:

```txt
PLATFORM-142 add user cache for profile requests
```

### Пример проверки commit message через Node.js

Это удобнее, чем shell-скрипты, потому что работает предсказуемее в кроссплатформенной среде.

```js
// scripts/check-commit-message.js
import fs from "node:fs";

// Git передает путь к временному файлу с сообщением коммита
const commitMessageFile = process.argv[2];
const commitMessage = fs.readFileSync(commitMessageFile, "utf8").trim();

// Пример шаблона: PROJECT-123 short description
const commitPattern = /^[A-Z]+-\d+\s.+$/;

if (!commitPattern.test(commitMessage)) {
  console.error(
    "Неверный формат коммита. Ожидается: PROJECT-123 short description",
  );
  process.exit(1);
}
```

Подключение через `Husky`:

```sh
node scripts/check-commit-message.js "$1"
```

### Подводный камень

Слишком жесткие правила на коммиты тоже вредят.

Если формат настолько сложный, что его приходится гуглить каждый раз, значит правило плохое.

## Кратко:

- Имена веток и коммиты должны быть предсказуемыми.
- Проверять формат лучше автоматически.
- Правило должно помогать, а не издеваться над людьми.

## Типы без полной миграции на TypeScript

Тут есть практичный промежуточный путь: `JSDoc + TypeScript checkJs`.

Это не замена TypeScript во всех сценариях, но это очень полезный шаг для JavaScript-проектов, особенно если:

- проект уже большой;
- полная миграция дорогая;
- хочется типовых подсказок и проверок уже сейчас.

### Почему JSDoc полезен

Он решает сразу две задачи:

1. Документирует код.
2. Дает редактору и TypeScript дополнительную информацию о типах.

### Пример с JSDoc

```js
/**
 * Загружает пользователя по идентификатору.
 *
 * @param {string} userId - Идентификатор пользователя.
 * @returns {Promise<{ id: string, name: string } | null>}
 */
export async function loadUser(userId) {
  const response = await fetch(`/api/users/${userId}`);

  if (!response.ok) {
    return null;
  }

  return response.json();
}
```

### Пример `tsconfig.json` для проверки `.js`

```json
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": true,
    "noEmit": true,
    "strict": true
  },
  "include": ["src/**/*.js"]
}
```

Пример команды:

```json
{
  "scripts": {
    "typecheck": "tsc -p tsconfig.json"
  }
}
```

### Что это реально дает

- автодополнение в редакторе;
- проверку параметров и возвращаемых значений;
- меньше шансов случайно передать число туда, где ждут строку.

### Пример ошибки, которую поймает проверка

```js
/**
 * @param {string} word
 */
function printWord(word) {
  console.log(word.toUpperCase());
}

printWord(123);
// TypeScript при checkJs скажет, что число сюда передавать нельзя
```

### Где у подхода границы

Надо честно понимать ограничения:

- JSDoc не заменяет полноценную миграцию на TypeScript;
- сложные generic-случаи писать неудобнее;
- дисциплина все еще нужна, комментарии можно забросить.

Но как промежуточный шаг это очень рабочая история.

## Кратко:

- `JSDoc + checkJs` помогает типизировать JavaScript без полной миграции.
- Это одновременно документация и базовая проверка типов.
- Для больших и сложных систем TypeScript все равно обычно сильнее.

## Генерация документации из JSDoc

Если уже пишешь JSDoc, из него можно вытаскивать документацию почти бесплатно.

Это особенно полезно для:

- SDK;
- внутренних библиотек;
- модулей с публичным API;
- микросервисных клиентов.

### Пример функции с JSDoc

```js
/**
 * Создает клиента для работы с API пользователей.
 *
 * @param {string} baseUrl - Базовый URL сервиса.
 * @returns {{
 *   getById(userId: string): Promise<{ id: string, name: string } | null>
 * }}
 */
export function createUserApi(baseUrl) {
  return {
    async getById(userId) {
      const response = await fetch(`${baseUrl}/users/${userId}`);

      if (!response.ok) {
        return null;
      }

      return response.json();
    },
  };
}
```

### Что важно помнить

Документация полезна только тогда, когда она живет рядом с кодом и обновляется вместе с ним.

Если документацию надо отдельно переписывать руками, она быстро протухает.

> **Важно**
> Лучше короткая, но актуальная документация, чем огромная и устаревшая.

## Кратко:

- JSDoc удобно использовать как источник правды для API.
- Автогенерация документации снижает вероятность рассинхрона.
- Особенно хорошо это работает для SDK и библиотек.

## Как внедрять правила в legacy-проект

Вот тут обычно и начинается настоящая боль.

Потому что если взять старый проект и просто запустить на нем все проверки разом, можно получить тысячи ошибок.

Это не значит, что идея плохая. Это значит, что внедрять надо с головой.

### Рабочий поэтапный план

#### Шаг 1. Зафиксировать базовые инструменты

- `EditorConfig`
- `ESLint`
- `Stylelint`
- `Prettier`
- базовые hooks

#### Шаг 2. Прогон на весь проект

Сначала просто посмотри масштаб бедствия:

```json
{
  "scripts": {
    "lint": "npm run lint:js && npm run lint:css && npm run typecheck"
  }
}
```

#### Шаг 3. Включить автоматический фикс там, где он безопасен

```json
{
  "scripts": {
    "fix": "npm run lint:js:fix && npm run lint:css:fix && npm run format"
  }
}
```

#### Шаг 4. Жестко проверять только измененные файлы

Это почти всегда самый безболезненный старт.

#### Шаг 5. Постепенно подчищать старые зоны

Можно:

- выделять отдельные модули;
- вводить правило "потрогал файл, приведи его в порядок";
- закрывать старые проблемы по очереди.

### Подводные камни

- Не надо в один merge request тащить и рефакторинг, и бизнес-логику, и тотальное форматирование.
- Не надо одновременно включать 100 новых правил.
- Не надо ломать скорость команды ради формальной победы.

### Пример правила "починил и пошел дальше"

```js
// Было
var users = [];

function addUser(name) {
  users.push({ name: name });
}

// Стало
const users = [];

function addUser(name) {
  users.push({ name });
}
```

Небольшое улучшение, но если так делать системно, кодовая база постепенно выравнивается.

## Кратко:

- Legacy надо лечить поэтапно.
- Начинай с измененных файлов, а не с войны со всей кодовой базой.
- Автоматический фикс сильно снижает боль внедрения.

## Codemods и AST: когда regex уже не вывозит

Иногда нужно массово преобразовать код по умным правилам.

Например:

- заменить устаревший API;
- переписать синтаксис;
- перевести часть кода на новый стиль;
- сделать миграцию после обновления фреймворка.

И вот тут обычный поиск и замена быстро заканчивается плохо.

### Почему regex опасен

Потому что код это не просто текст. У него есть структура.

Например, заменить все `var` на `const` через regex звучит бодро, но может сломать код:

- у `var` и `let/const` разная область видимости;
- часть переменных потом переназначается;
- где-то объявление находится внутри цикла или условия.

### Что делать правильно

Использовать AST и codemods.

Подход такой:

1. Парсим код в дерево.
2. Ищем нужные узлы.
3. Меняем только то, что реально нужно.
4. Генерируем код обратно.

### Упрощенный пример трансформации

```js
// Пример идеи, а не готовый production-скрипт
export default function transformer(fileInfo, api) {
  const j = api.jscodeshift;
  const root = j(fileInfo.source);

  // Ищем объявления переменных
  root.find(j.VariableDeclaration, { kind: "var" }).forEach((path) => {
    const declarations = path.value.declarations;

    // Превращаем var в const только если все переменные сразу инициализированы
    // и дальше не переназначаются. В реальной жизни нужна дополнительная проверка.
    const canBeConst = declarations.every((declaration) => declaration.init);

    if (canBeConst) {
      path.value.kind = "const";
    }
  });

  return root.toSource();
}
```

### Важно

Код-мод это не магия. Его тоже надо тестировать на реальных кейсах.

Особенно опасны:

- теневые переменные;
- переопределения;
- разные области видимости;
- нестандартный синтаксис проекта.

## Кратко:

- Для массовых умных изменений нужен AST, а не regex.
- Codemods сильно экономят время на миграциях.
- Любой codemod надо прогонять на тестовых кейсах перед большим запуском.

## Как написать свое правило для ESLint

Когда стандартных правил не хватает, можно написать свое.

Это имеет смысл, если у вас есть реальное проектное требование, которое:

- регулярно нарушают;
- сложно ловить review-глазом;
- можно формализовать.

Пример из жизни: команда решила использовать CSS Modules и не разрешать строковый `className`.

### Что хотим запретить

```jsx
export function Button() {
  return <button className="button">Save</button>;
}
```

### Что хотим видеть

```jsx
import styles from "./Button.module.css";

export function Button() {
  return <button className={styles.button}>Save</button>;
}
```

### Пример простого правила ESLint

```js
// rules/no-string-classname.js
export default {
  meta: {
    type: "problem",
    docs: {
      description: "disallow string literals in JSX className",
    },
    schema: [],
    messages: {
      noStringClassName: "Не используй строковый className. Используй CSS Modules.",
    },
  },
  create(context) {
    return {
      JSXAttribute(node) {
        // Ищем только атрибуты className
        if (node.name?.name !== "className") {
          return;
        }

        // Если значение атрибута строка, считаем это нарушением
        if (node.value?.type === "Literal" && typeof node.value.value === "string") {
          context.report({
            node,
            messageId: "noStringClassName",
          });
        }
      },
    };
  },
};
```

### Как подключить правило

```js
// eslint.config.js
import noStringClassName from "./eslint/rules/no-string-classname.js";

export default [
  {
    plugins: {
      local: {
        rules: {
          "no-string-classname": noStringClassName,
        },
      },
    },
    rules: {
      "local/no-string-classname": "error",
    },
  },
];
```

### Почему тут важны тесты

Без тестов кастомное правило очень быстро становится источником ложных срабатываний.

Нужно проверять как минимум:

- валидные примеры;
- невалидные примеры;
- edge-cases;
- разные варианты синтаксиса JSX.

### Пример тестовой идеи

```js
// Тут только идея набора кейсов
const valid = [
  'const node = <div className={styles.card} />;',
  'const node = <div className={getClassName()} />;',
];

const invalid = [
  'const node = <div className="card" />;',
];
```

> **Важно**
> Кастомное правило должно решать конкретную боль команды. Не надо писать правила ради факта, что "мы можем".

## Кратко:

- Свои ESLint-правила нужны только под реальные проектные ограничения.
- Писать их надо на AST, а не на строках.
- Без тестов кастомный линт быстро превращается в помеху.

## Code review после внедрения правил

Один из самых приятных эффектов внедрения линтеров и форматтеров в том, что из review уходит куча мелкого мусора.

Люди перестают писать:

- "тут пробел не там";
- "а давай стрелочную функцию";
- "перенеси запятую";
- "кавычки не те".

И review начинает заниматься тем, чем должен:

- логикой;
- архитектурой;
- edge-cases;
- рисками;
- поддерживаемостью.

### На что смотреть в review, когда формат уже автоматизирован

- корректен ли сценарий;
- нет ли лишней связанности;
- правильно ли обработаны ошибки;
- нет ли проблем с асинхронностью;
- не ломается ли публичный API;
- есть ли тесты;
- не растет ли техдолг в опасных местах.

### Мини-пример review-мышления

```js
export async function saveProfile(data) {
  const response = await fetch("/api/profile", {
    method: "POST",
    body: JSON.stringify(data),
  });

  return response.json();
}
```

Форматирование тут может быть идеальным, но вопросов все равно хватает:

- а что при `response.ok === false`;
- а где `headers: { "Content-Type": "application/json" }`;
- а что если сервер вернет не JSON;
- а нужно ли делать retry или хотя бы нормальную ошибку.

Вот про это review и должен быть.

## Кратко:

- Автоматизация вычищает из review мелкий шум.
- После этого можно смотреть на архитектуру и поведение.
- Хороший review обсуждает риски, а не отступы.

## Владение кодом, SDK и документация

Когда проект большой, полезно иметь понятные границы ответственности.

Например:

- у каждого модуля есть владелец;
- у каждого SDK есть публичный API;
- у важных библиотек есть документация;
- изменения в чувствительных частях смотрят ответственные люди.

### Зачем это нужно

Если все могут менять все без структуры, в какой-то момент никто уже не понимает:

- кто знает этот код;
- кто отвечает за совместимость;
- кто должен смотреть review;
- где искать документацию.

### Хорошая практика для SDK

- скрывать детали общения с микросервисом внутри SDK;
- наружу отдавать понятный API;
- документировать методы рядом с кодом;
- версионировать пакет аккуратно.

Пример:

```js
/**
 * Клиент API пользователей.
 */
export class UsersSdk {
  /**
   * @param {string} baseUrl
   */
  constructor(baseUrl) {
    this.baseUrl = baseUrl;
  }

  /**
   * Возвращает пользователя по id.
   *
   * @param {string} userId
   * @returns {Promise<{ id: string, name: string } | null>}
   */
  async getById(userId) {
    const response = await fetch(`${this.baseUrl}/users/${userId}`);

    if (!response.ok) {
      return null;
    }

    return response.json();
  }
}
```

### Edge-case: "а давайте дергать микросервис напрямую из любого места"

Так можно, но недолго.

Потом начинаются:

- дублирование запросов;
- разъезд контрактов;
- хаос с обработкой ошибок;
- боль при изменении API.

SDK или слой API-клиентов как раз нужен, чтобы это не размазывалось по всему проекту.

## Кратко:

- У больших систем должны быть владельцы и границы ответственности.
- SDK полезен как единая точка входа к сервису.
- Документация рядом с кодом сильно упрощает поддержку.

## План внедрения без истерики

Если собрать все вместе, то нормальный порядок действий обычно такой.

### 1. Сначала база

- добавить `EditorConfig`;
- подключить `ESLint`;
- подключить `Stylelint`;
- подключить `Prettier`;
- включить проверки в редакторе.

### 2. Потом локальная автоматизация

- добавить `Husky`;
- добавить `lint-staged`;
- настроить проверку коммитов при необходимости.

### 3. Потом серверная защита

- включить CI;
- защитить основные ветки;
- запретить merge без успешных проверок.

### 4. Потом постепенная расчистка legacy

- чинить сначала измененные файлы;
- отдельно планировать крупные cleanup-задачи;
- не смешивать бизнес-логику и массовое форматирование в одном PR.

### 5. Потом точечные улучшения

- JSDoc;
- типовые проверки через `checkJs`;
- кастомные ESLint-правила;
- codemods для миграций.

> **💡 Совет**
> Самая частая ошибка внедрения в том, что команда пытается сделать все сразу. Так почти всегда получается сопротивление, усталость и саботаж.

## Кратко:

- Внедрение должно быть пошаговым.
- Сначала автоматизируй рутину, потом ужесточай правила.
- Главное не "включить все", а сделать процесс устойчивым.

## Финальная мысль

Все эти линтеры, форматтеры, хуки и пайплайны нужны не для того, чтобы мучить разработчика.

Они нужны для того, чтобы:

- меньше спорить;
- быстрее читать код;
- быстрее вводить новых людей в проект;
- раньше ловить ошибки;
- не тащить хаос в прод.

Хороший процесс обычно сначала всех раздражает, потому что заставляет перестать делать как попало. Но потом команда привыкает, review ускоряется, кодовая база становится ровнее, а поддержка начинает стоить заметно дешевле.

И вот тогда становится видно, что весь этот "занудный порядок" был нужен не ради порядка. Он был нужен ради скорости.

## Кратко:

- Порядок в коде нужен не ради эстетики, а ради эффективности.
- Лучший процесс тот, который поддерживается автоматически.
- Если правила снимают шум и экономят время, значит они работают.
